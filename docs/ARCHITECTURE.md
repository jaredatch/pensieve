# ARCHITECTURE.md — Pensieve

The durable shape of the system: layers, boundaries, and the key abstractions the Executor must respect. The Planner keeps this current; the Executor treats the boundaries here as load-bearing (the Never list forbids bypassing them). It is reverse-engineered from the code and documents *what is*, only where an agent could otherwise get it wrong.

## 1. Layers

Four layers, dependencies point downward only. Views never touch the filesystem or `FileManager`; services never import SwiftUI (one exception: `SyncScheduler` imports it for its `@AppStorage`-backed background-sync preference).

```
Views (SwiftUI + named   Pensieve/Views/**        presentation only; @Query, @Bindable, @Environment(\.modelContext)
       AppKit bridges)
   │
   ▼
ViewModels (@Observable)  Pensieve/ViewModels/**    UI state + intents; hold service protocols; take a ModelContext per call
   │
   ▼
Services (protocols)      Pensieve/Services/**       all business logic + the only code that talks to the filesystem
   │
   ▼
Models (@Model) + FS      Pensieve/Models/**         SwiftData metadata  +  ~/.pensieve/skills/{dir}/SKILL.md body
```

Beside the layers: `AppRuntime` (`Pensieve/AppRuntime.swift`, process-scoped; §2 "The resident runtime") owns the `ModelContainer` and the long-lived view models and services, and `Pensieve/Utilities/` holds the SwiftUI-free helpers shared across layers (`PathConstants`/`Constants` paths, `DeployIndex`, `ListRows`, `AppSignal`, `RelativeTime`, `GitHeadStamp`, `DogfoodMode`).

**The view layer is SwiftUI everywhere except seven named AppKit bridges.** Each is a narrow first-party hosting adapter, not private-view introspection, and new AppKit use needs the same justification (use the AppKit control only where a SwiftUI wrapper visibly diverges from the tier-1 pattern):

- **The sidebar** is an `NSOutlineView` in `.sourceList` style, hosted by the `NSViewRepresentable` `SidebarOutline` (`Views/MainWindow/SidebarOutline.swift`; `SidebarOutlineController` is its data source/delegate). `SidebarRows.items(showsMachines:)` builds the static section list and hands it to the outline; the selection binding is written only from a user selection.
- **The tag editor** is an `NSTokenField` hosted by the `NSViewRepresentable` `TagTokenField` (`Views/SkillViews/TagTokenField.swift`); its coordinator owns the editing baseline and completion. SwiftUI has no token field, so Pensieve uses the AppKit control.
- **The editor** is the vendored CodeMirror running in a hardened `WKWebView`, hosted by `MarkdownEditorWebView` (`Views/SkillViews/Editor/`). Canonical skill bodies — a sync pull's included — reach it through `readBody` and the marshalled bridge; conflict sides, diffs, and past versions render inert and never enter it (CONVENTIONS §14).
- **Skill export** uses `NSSavePanel` in `SkillExportPanel` for the filename, folder creation, and replacement confirmation. `SkillExportModel` reads bytes through the library’s `SkillStore` and writes through `FileService`. The save panel and errors attach to the main window.
- **Directory picking** uses `NSOpenPanel` in `AddProjectSheet` and in `ContentView.importFromFolder` (Import from Folder…).
- **Process lifecycle** is `PensieveAppDelegate` (`NSApplicationDelegate` via `@NSApplicationDelegateAdaptor`): it keeps the process alive after the last window closes and reopens the main window. (`SyncScheduler`, a service, also imports AppKit for `NSWorkspace.didWakeNotification`.)
- **The window's close veto** is `WindowCloseGuard` (`Views/MainWindow/WindowCloseGuard.swift`): a delegate proxy on the main window that answers `windowShouldClose` for an unsaved draft and forwards every other delegate call to SwiftUI's own delegate — SwiftUI has no close hook on macOS 14.

The `pensieve-conventions` project skill (`.claude/skills/`) encodes this as "three-layer pattern, no exceptions." Treat it as binding.

## 2. Key boundaries & abstractions

**`FileServiceProtocol` is the single filesystem chokepoint — the most load-bearing boundary in the app.** Every file read, write, symlink, hash, copy, and directory op goes through it (`Pensieve/Services/FileService.swift`). No service, view model, or view performs file *I/O* via `FileManager` directly. This is what makes the services unit-testable against temp dirs and lets sync intercept every mutation. Two narrow, allowed exceptions exist and don't count as I/O: `PathConstants` (re-exported as `Constants`) calls `FileManager.default.homeDirectoryForCurrentUser` purely to *derive* home-relative base paths, and `AddProjectSheet` uses `NSOpenPanel` to *pick* a directory (a UI affordance). Actual reads/writes of those paths still go through `FileService`. Two leaf primitives sit deliberately outside it: `GitService` (the sanctioned subprocess exception, below) and `SyncLock`, a raw-POSIX advisory-lock primitive that creates its own lock directory with `FileManager` because `FileService` models skill-tree CRUD, not file descriptors (its doc comment carries the rationale). The rule to enforce: no I/O outside `FileService`. The protocol also exposes `isExecutableFile(at:)` for agent detection and the PLAN-19 binary boundary: `readData`, descriptor-bound `copyFile`, and `isUserExecutableFile`. Those operations let install vendor arbitrary regular-file assets without following a symlinked leaf and preserve the owner-executable bit. `copyFile` writes a temporary sibling through its descriptor, then renames it over the destination after the copy succeeds. A failure leaves the destination intact. A destination symlink's target and a hard link's other names keep their bytes.

**The dual source of truth.** Skill *metadata* lives in SwiftData (`Skill` `@Model`); the skill *body* lives on disk at `~/.pensieve/skills/{directoryName}/SKILL.md`. The markdown body is **never** duplicated into the database. `Skill.directoryName` (the slug) is the join key between the two. `Skill.canonicalPath` computes the on-disk path. This split is deliberate and is the foundation the cross-machine sync engine (BETTER) is built on: sync moves the self-describing files + a small manifest, and each machine rebuilds its SwiftData locally — never syncs the database.

**The self-describing store + the manifest overlay (PLAN-07/17/19/23/36).** `~/.pensieve` is a complete, portable, rebuildable, continuously-current source of truth: the contract the sync engine moves between machines. **(1)** PLAN-07 made an owned skill's `SKILL.md` carry standard **YAML frontmatter** with `name` + `description` (parsed by Yams, written by the canonical writer). PLAN-38 later replaced direct Yams reads with `CheckedYAMLLoader`. A GitHub-installed skill is instead vendored as its complete directory, byte-pristine, so scripts, assets, and executable mode remain faithful to upstream. Pensieve-authored and legacy-imported skills use the canonical writer; adopting an existing skill links provenance without rewriting its files. **(2)** Pensieve bookkeeping lives in the **per-entity YAML manifest overlay** under `~/.pensieve/manifest/`, outside skill bytes (`ManifestService`). Manifest schema v5 retains the schema-v3 `InstalledOrigin` block and schema-v4 deploy-intent files under `manifest/deploys/<machine-id>/<slug>.yaml`. Each file's `platforms` list is user-wide intent; an optional `projects` list carries project identity keys with their own platform lists. Category rules also live in the overlay; a project's identity is published per machine in `machines/<id>.yaml`, and `manifest/projects.yaml` is the constant `projects:` — older builds' entries still parse and union. The governing rule remains **sync durable facts, compute volatile flags locally**: update-check state and realized assignment ledgers live only in local SwiftData. Observed machine state is synced outside the manifest at `machines/<machine-id>.yaml`, where each machine writes only its own file. A project may carry a display-only, home-abbreviated path; the path is never identity or an input to file operations, and local absolute paths and secrets never enter machine state. Older readers fail safe, and the write-side schema guard prevents an older build from overwriting a parsed newer manifest.

**The rebuild/migrate triad (PLAN-07).** Three services keep disk ⟷ SwiftData convergent, all over the `FileService` + `ManifestService` boundary, **none touching git**: **`StoreRebuildService`** reconstructs SwiftData from disk + manifest — the clone-bootstrap for a fresh machine (files but an empty DB) and the post-pull refresh PLAN-08 runs. A convergent insert/update/delete reconcile that **admits only skills with required frontmatter** (`name`+`description` both non-empty; a body-only / malformed file is skipped + warned, never a degraded row), that **bails mutating nothing** when the manifest declares a `schema_version` newer than this build understands (`ManifestService.read` throws `unsupportedSchema`) — rather than reconciling off an empty snapshot, which would reset overlay-backed fields + delete every category (PLAN-07/07.4 review; a same-schema *corrupt* manifest bails the same way — `read` throws `corruptManifestFile` on an unparseable file, a missing `name`/`slug`, or a list-shaped membership field that is not a sequence, staying tolerant only on additive scalars — PLAN-10), and that is idempotent (a no-change rebuild is all-zero). An overlay is authoritative **only when present**: for a skill whose row already exists but whose `manifest/skills/<slug>.yaml` is ABSENT, the reconcile **preserves** the row's overlay-backed fields (scope/tags/cursor/origin/createdAt) rather than resetting them to defaults — the manifest is silent, not authoritative-empty — updating only the on-disk-frontmatter name/description (PLAN-12 / 12.3; the data-loss root that the import-side overlay write, this preserve rule, and `LaunchReconciler.manifestHasContent` now guard in depth). **`StoreMigrationService`** is the one-time, idempotent, launch-time backfill that brings every existing owned skill up to the self-describing model (frontmatter + overlay) **without losing a description** that lived only in the file or `cursorConfig` (origin-aware name precedence, file-preserving description precedence, row backfill). **`ManifestService`** keeps the overlay current at the **enumerated maintenance sites** — a skill create / **import** / metadata-edit / delete, a category rule change, a project register / remove — each regenerates the affected manifest from SwiftData, so a rebuild reproduces the live store. Bulk **import** *was* the one deliberately-deferred site (the 07.3 scoping) — an imported skill's overlay was left for the next single mutation or the one-time launch migration to write — but **PLAN-12 / 12.3 retired that deferral**: the launch rebuild now treats the manifest as authoritative *and* the migration runs once-ever, so a deferred (overlay-less) imported skill would be reset to defaults on the next relaunch. Import therefore regenerates the overlay immediately after its save, exactly like every other synced-state mutation, so no rebuild or sync (PLAN-08) can ever consume a store with a missing overlay. **The regeneration is atomic:** `ManifestService.write` builds the whole manifest in a UUID-unique sibling tree *outside* the store (`~/.pensieve.manifest-build-<uuid>.tmp`, same volume, so sync's `git add -A` can never stage a partial build) and then swaps it in via `FileService.replaceItem` (`renamex_np` `RENAME_SWAP`, or an atomic move on first write), so a write that fails part-way leaves the previous `manifest/` byte-for-byte intact — the launch rebuild and the daemon never observe a half-written manifest (no schema-only tree that would delete categories, no partial overlay set). Because the temp tree is built fresh, there are no stale files to prune. Together, the import-side overlay write, rebuild preservation of an existing row when its overlay is absent, and atomic manifest writes close every deferred/partial-manifest data-loss path the 12.3 launch rebuild could otherwise hit. The load-bearing invariant across every write path: `name` and `description` are always non-empty (name required at create + slug hardened non-empty; description falls back to the name), so no skill is ever dropped on a fresh-machine rebuild. PLAN-08 adds `GitService` + the `SyncEngine` on top of this store; PLAN-09 the body-conflict UX.

**The sync layer (BETTER-1, PLAN-08) — three services beneath the store.** Sync is pure plumbing over the already-portable PLAN-07 store: `~/.pensieve` becomes a **git working tree**, and each machine rebuilds its SwiftData locally, so the database is **never** synced — it and every out-of-tree app file live under `~/Library/Application Support/Pensieve` (`Constants.pensieveAppSupportDir`), deliberately outside the synced `~/.pensieve` root. Three services (`Pensieve/Services/`): **`GitService`** is the app's **first subprocess** — a synchronous, throwing wrapper over `/usr/bin/git` (absolute path). It is the one **sanctioned exception** to the `FileService` chokepoint: git owns `.git` and its own writes, reached only here. Arguments are **always** an array (`Process.arguments`), never a shell string, so there is no command-injection surface; every op taking a user-supplied remote/path positional puts a `--` end-of-options terminator before it (git parses a leading-dash or `--upload-pack=<cmd>` positional as an *option* it would execute — a git-option-injection class distinct from shell injection). The child environment is built explicitly for a **Finder/Spotlight launch** (which inherits neither the login-shell PATH nor the ssh-agent socket): PATH augmented with the standard git/ssh locations, `GIT_TERMINAL_PROMPT=0` to fail fast instead of hanging on a TTY-less prompt, `SSH_AUTH_SOCK` passed through, and the Pensieve-owned `GIT_ASKPASS`/`PENSIEVE_GIT_*` vars stripped-then-set so a `.sshAgent`/`nil` op can never ride a stale parent askpass. **`CredentialStore`** (`KeychainCredentialStore`) is the Keychain boundary: an HTTPS PAT is stored in a **Pensieve-namespaced `kSecClassGenericPassword`** item whose service string is derived from the bundle identifier — `<bundle-id>.git.<host>`, i.e. `com.jaredatch.Pensieve.git.<host>` in Release and `com.jaredatch.Pensieve.debug.git.<host>` in a Debug build, so a store/delete can never touch a non-Pensieve credential and a Debug build can never read or replace a production one. The GitHub install credential uses the separate `<host>#install` slot, never the sync credential. The PAT reaches git only through the **child process environment** via a secret-free `GIT_ASKPASS` helper — never argv (invisible to `ps`), never `.git/config` or a cleartext file (the helper itself lives out-of-tree at `Constants.gitAskpassHelperPath`, 0700, written through `FileService.writeExecutableFile`). ssh remotes store no app-side secret (ssh-agent passthrough). The connect-a-remote onboarding (`SyncSetupModel.parseRemote`) is a strict **transport allowlist** — https / ssh / scp-style only; `ext::`/`fd::`/remote-helper syntax, a leading `-`, and https-userinfo (`user:tok@host`) are all rejected before any URL reaches `GitService`. **`SyncEngine`** ties the store to git: `snapshot → manifest write → install the `merge=union` `.gitattributes` for the LIST-shaped manifest files (category files + the now-constant `projects.yaml`, kept for older builds' entries) → commit → pull --rebase → rebuild → push`. Concurrent set-edits (a skill joins a category) auto-merge via git's built-in union driver + dedup-on-read; a genuine same-entity body/overlay conflict is **aborted (restoring the exact pre-pull tree) and surfaced structurally** as `.conflicted(paths)` — never silently clobbered, never a raw `<<<<<<<` marker — with the local commit left unpushed for a later resolvable sync. That `.conflicted` outcome + the `SyncStatusView` indicator are the exact seam **PLAN-09** consumes for the diff-and-pick resolution sheet. A `/security-review` over this surface (PLAN-08 / 08.5-a) found no exploitable path.

A git remote answer is absent only on a known absent result: a successful empty URL, no origin in a readable repository, or a no-follow `.git` lookup reporting absence followed by confirmation that the store root is still a directory. Other failures are unknown and stop sync before preparation or writes. A missing store folder remains unknown. AppRuntime keeps ordered git-usability results in memory, probes off the main actor, and shares the resulting configuration with Settings and sync status. Unusable git preserves active sync and conflict states and pauses scheduled cycles until a probe or successful git operation reports recovery. Configuration reads and git evidence have separate ordering. A read that skips git cannot replace usability evidence. Completed configuration answers share one clock across runtime refreshes. An older read never replaces a newer answer. A configuration-read failure with usable git permits scheduled cycles to retry the repository. Settings offers Connect only after a completed configuration read proves absence. A cycle result never changes that answer or retires an outstanding read. Branchless stores can return no remote even with an origin. Runtime configuration refreshes run off the main actor, including window appearance and conflict completion. Those window callbacks reuse known usability without probing. The older launch-ingestion remote check remains synchronous. The read after a cycle supplies its current URL, absence or error. Cycle failures retain their own message through the single-line formatter.

**The GitHub install and skill-update layer (BETTER-4 / BEST-1 provenance slice, PLAN-19).** `SkillInstallURL` parses the supported GitHub repository, directory, and `SKILL.md` browser links; `InstallRemotePolicy` is the stricter stored-coordinate admission boundary and reconstructs the only clone remote git receives. `SkillInstallService` shallow-fetches, performs the bounded repository discovery, vendors complete regular-file trees, handles collisions and rename, adopts existing skills without changing their bytes, previews a pinned update, and atomically re-vendors an applied update under `sync.lock`. It writes the schema-v3 `InstalledOrigin` through `ManifestService.upsertSkillOverlay` and refreshes the SwiftData cache. `UpdateCheckService` batches linked skills by repository/ref, resolves heads with credential-isolated `ls-remote`, shallow-clones moved heads once, compares per-skill git trees, pins the checked commit/date/tree locally, computes stable local drift on demand, and never writes the synced overlay during a check. Both services use only the `github.com#install` credential or anonymous access; they never fall back to the sync credential. `SkillInstallViewModel` drives paste → fetch → pick → vendor/adopt; `SkillProvenanceViewModel` derives links, dates, drift, and per-skill check state (the list's filter and sort belong to `SkillListQuery`, a pure function over the skills, a `SkillListSpec`, the deploy index, and the categories — PLAN-29); `UpdatesViewModel` derives the notice/list (surfacing each update's validated source repository and in-repo path), pinned `SKILL.md` diff, explicit drift confirmation, re-check, and batch apply. These view models keep filesystem, git, hashing, and other expensive service work off the main actor; their `@MainActor` completion paths perform the compact SwiftData fetches and merges that update presented state.

Update checks leave a source batch's skill state unchanged when git is unusable or the network fails during its head read or clone. A run reports one environment error while saving the sources that answered. Authentication and missing repositories remain per-skill errors. A run advances the automatic-check timestamp unless it has an environment failure and no head read answered. A local operation or save failure is reported and waits for the normal interval before another automatic run. The service owns result persistence. The main-context presentation merge does not save unrelated editing state. A failed service save is reported alongside any environment error. Empty and all-authentication runs count. An all-offline run stays due for the next launch. Any completed check with an environment failure and no answered source suppresses further activation retries in that session. Other outcomes leave the deferral clear. A new launch, a manual check starting, or recovery from known-unusable git clears it. A manual check that fails for the environment sets it again. Another usable answer while git is already usable does not retry an offline check. Local read and save failures do not defer checks. Manual checks remain available. Environment failures during a clone or tree read preserve the whole batch. Other clone failures affect only pending skills. One classifier carries actual usability evidence to the runtime, with at most one diagnostic probe per batch after the run preflight. Developer-tools text in command stderr is only a hint because a repository can control it. A diagnostic probe must confirm it before the error becomes a host failure. A later local failure preserves that evidence and still counts toward the interval. Positive update-check evidence refreshes the remote even with background sync off.

**The resident runtime (BETTER-2, PLAN-23).** `AppRuntime` owns the explicit `ModelContainer`, long-lived platform/library/sync models, file watcher, `SyncScheduler`, and the asynchronously bootstrapped `SyncCoordinator`. It belongs to the process, not a window. `PensieveApp` injects that one runtime into the main window, Settings, and `MenuBarExtra`; `PensieveAppDelegate` keeps the process alive after the last window closes and recreates the main window on reopen. `SMAppService.mainApp` provides the user-controlled Launch at Login setting. The scheduler queues a launch run, ticks every 900 seconds, listens for wake, and debounces synced-state mutations for 30 seconds. It permits one cycle at a time and coalesces overlap into one follow-up. Background cycles do not run before coordinator bootstrap and launch ingestion are both ready, while sync is conflicted, without a configured remote, or while another actor holds `sync.lock`. Sync Now is refused from every entry point while the store is conflicted, and a conflict resolution can't start while a cycle is in flight, so the two never overlap.

`SyncCoordinator` is a `@ModelActor` entered from detached work, so its synchronous engine and SwiftData work do not occupy the main actor. Each cycle creates a fresh `ModelContext`. `SyncEngine` still owns the one `sync.lock` acquisition; its `prepare` hook runs after the pre-write guards and immediately before snapshotting. The coordinator uses that hook to rebuild stale SwiftData after an external fast-forward and then publish this machine's `machines/<id>.yaml` state, so the snapshot cannot revert a CLI pull. A successful cycle returns to the main actor for `PostSyncConvergence`: `DeployReconciler` self-heals after every success, and a HEAD-advancing cycle runs category and intent reconcilers in order on another fresh context. The app and CLI share bounded `daemon-status.json` and `daemon.log` audit artifacts through a dedicated leaf lock.

**The retained daemon CLI (PLAN-12/15/16, superseded scheduling in PLAN-23).** The SwiftData-free `pensieve-daemon` executable remains embedded for SSH use. Its `status`, `log`, `deployed`, and degraded `run` commands keep their existing contracts; `run` is still a clean-tree, fast-forward-only downstream pull and never becomes a second resident peer. Since v0.14.0 (#24), the app bundles no LaunchAgent plist and nothing registers the daemon with launchd. The daemon target's explicit source list remains a structural SwiftData/SwiftUI-free boundary.

**Update and release flow (PLAN-18).** The release script publishes the root `appcast.xml` to this repo's default branch, `master`. Sparkle reads the URL embedded in the app. `SUFeedURL` names `master`. Builds up to v0.14.0 name `main` and reach the same file through GitHub's rename redirect, so `main` must never be recreated. Sparkle orders updates by build number, so `script/build-number.sh` sets it to the commit count plus `BUILD_NUMBER_OFFSET`, which keeps every new build above the ones already shipped. Each appcast item points to a versioned DMG release asset such as `https://github.com/jaredatch/pensieve/releases/download/v0.11.0/Pensieve-0.11.0.dmg`; the Homebrew tap cask (`jaredatch/homebrew-tap/Casks/pensieve.rb`) points at that same versioned asset after the release script writes the real SHA-256. Updates replace `/Applications/Pensieve.app` in place. Launch at Login addresses that main bundle. The legacy-agent migration ran in v0.12.0–v0.13.0 and was removed in v0.14.0.

**The deploy dispatch: `PlatformTarget.usesSymlinks`.** `PlatformTarget` (`.claudeCode`, `.grok`, `.cursor`, `.codex`, `.openClaw`, `.hermes`) decides deploy mechanism by `usesSymlinks` (`Pensieve/Models/PlatformTarget.swift`):
- `claudeCode`, `grok`, `codex`, `openClaw`, `hermes` → **symlink** via `LinkService`. `LinkService.link(...)` throws `LinkError.platformDoesNotUseSymlinks` if called for Cursor — the boundary is enforced, not assumed.
- `cursor` → **compiled `.mdc`** via `CursorCompiler`. Cursor is the *only* platform with per-platform adapter config; `LinkService.linkPath`/`targetPath` return `""` for it by design.

`PlatformViewModel` dispatches on `usesSymlinks` to pick the service. OpenClaw and Hermes (PLAN-04), then Grok (PLAN-22), joined the symlink branch exactly this way — a new `PlatformTarget` case plus `Constants` paths, no change to `LinkService`'s switch shape. A future generic custom-agent adapter (deferred from GOOD-2) would do the same. Hermes is the one non-flat target: it nests under a category (`~/.hermes/skills/{category}/{name}`, default category `pensieve`); the symlink mechanism is otherwise identical.

**Project-scope capability: `PlatformTarget.supportsProjectScope`** (PLAN-05; PLAN-22). A second, orthogonal capability flag decides whether a target can be deployed into a *project* directory at all. `LinkService.link` derives `projectScopeUnsupported` from this flag (the old hardcoded `case .openClaw, .hermes` switch is gone). Claude Code, Grok, Codex, and Cursor have project-level skill paths and return `true`; OpenClaw and Hermes are user-wide-only. The deploy UI threads a `DeployTarget` (`.userWide` or `.project(Project)`) and filters its agent list through `PlatformViewModel.deployablePlatforms(forProject:)` — in project mode the list is `installedPlatforms ∩ {claudeCode, grok, cursor, codex}`, so OpenClaw/Hermes simply don't appear while a project is selected. This **supersedes** PLAN-04's earlier statement that PLAN-05 would lift `projectScopeUnsupported` for OpenClaw/Hermes. `DeployRecord` carries an additive optional `projectID` (PLAN-05) recording which project a deploy targeted; it is **append-only/historical** — no live count or connected-state derives from it (the connected state is a filesystem read of symlink presence), so a removed deploy leaves its record behind by design.

**Per-machine deploy state (PLAN-16).** `deploy-state.json` under `pensieveAppSupportDir` records the realized deployment set on this machine in schema version 1, one record per `artifact_path`; `deploy-state.lock` serializes its read-modify-write mutations as a leaf lock. The file is never synced because it contains local absolute paths, local agent availability, and local project registrations. GUI deploy/remove writes update it non-fatally after the link/compile succeeds, and launch backfill re-derives it from owned symlinks plus SwiftData `DeployRecord` history, preserving timestamps for surviving paths. The daemon consumes it for Cursor ownership instead of slug inference, and `pensieve-daemon deployed` reads it directly for SSH/headless listing. A machine whose GUI has never run post-PLAN-16 may have no records; that intentionally stops headless Cursor regeneration until a GUI launch backfills rather than risk claiming a user's colliding `.mdc`. In-app, `PlatformViewModel.deployIndex` is the observable in-memory cache of this file (`DeployIndex`, PLAN-29): rebuilt by `refreshDeployIndex()` when each of `PlatformViewModel`'s five mutation entry points completes (`deploy`, `remove`, `deployBatch`, `removeBatch`, and skill deletion's `removeAllDeploys` — the single operations from a `defer`, so a failed one refreshes too; the batches unconditionally; `removeAllDeploys` whenever it produced any outcome), after every convergence pass (each `runSuccessfulCycle`, reached from a `.synced` cycle or from `runAfterLaunchIngest()` at launch, and fired from a `defer` even when the deploy reconciler throws or a ledger reconciler reports failures), and after every launch backfill; it reports `.unavailable` — never empty — when the file cannot be read, and the lists read it instead of the filesystem, so the daemon CLI's prunes appear only at the next in-app mutation, launch, or `.synced` cycle, and the Deployments tab, whose switches read the filesystem per pair through the detail's snapshot, stays the truth where they disagree.

**Cross-machine project identity: `ProjectIdentityService`** (PLAN-05). A registered `Project` gets a stable cross-machine `identityKey`/`identityKind` so the same project folds to one identity on every machine even though its absolute `path` differs. The service reads `{project}/.git/config` *through `FileServiceProtocol`* (no `git` shell-out) only when `.git` is a directory, parses the `[remote "origin"]` url, and normalizes it (`host/path`, lowercased host, stripped `.git`/trailing-slash/user/port/query); when there is no normalizable remote it reads or creates a committed `.pensieve-project` UUID marker. A git worktree/submodule (`.git` is a *file*) intentionally falls through to marker identity — accepted for PLAN-05. Two entry points (PLAN-05 / 05.2-b): `identity(forProjectAt:)` is the write path — it creates the marker — and runs only at the registration "Add" action; `peekIdentity(forProjectAt:)` is a read-only probe for the Add Project sheet's live preview and **never writes**, so previewing a non-git directory and cancelling leaves no stray marker.

**Codex user-wide deploy (fixed in PLAN-04).** Earlier, `LinkService.linkPath(.codex, projectPath: nil)` aliased into `~/.claude/skills` — a user-wide Codex deploy wrote a symlink into Claude Code's directory. PLAN-04 fixed this: user-wide Codex now targets its own `~/.codex/skills/{name}` as a whole-directory symlink, and `targetPath(skill:platform:projectPath:)` is **scope-aware** (user-wide → the canonical directory; project-level → the `SKILL.md` file, unchanged). `SPEC.md`'s old "Codex is project-scoped only" line was itself made stale by this and has been corrected — Codex has a correct user-wide path now.

**Path construction is centralized in `Constants`** (`Pensieve/Utilities/Constants.swift`): `pensieveSkillsDir`, `claudeCodeUserSkillsDir`, `grokUserSkillsDir`, `codexUserSkillsDir`, `openClawUserSkillsDir`, `hermesUserSkillsDir`, `hermesDefaultCategory` (`pensieve`), `cursorUserRulesDir`, `claudeCodeProjectSkillsRel` (`.claude/skills`), `grokProjectSkillsRel` (`.grok/skills`), `codexAgentsRel` (`agents`). Never hardcode a `~/.claude`, `~/.grok`, `~/.codex`, `~/.openclaw`, `~/.hermes`, or `~/.cursor` path inline — add or reuse a `Constants` member, so a new agent's paths live in one place.

**Installed-agent detection: `AgentDetectionService`** (`Pensieve/Services/AgentDetectionService.swift`). Reports which agents are actually present so the deploy UI shows only the ones the user has. It reads the host only through an injectable `EnvironmentProbe` — directory/file existence delegate to `FileServiceProtocol` (the §2 boundary), and the one direct environment read is `PATH` for CLI resolution. An agent counts as installed on any signal: its config dir, app bundle, or an **executable** CLI on `PATH` (the PATH probe uses `FileServiceProtocol.isExecutableFile`, so a present-but-non-executable shadow file no longer false-positives — PLAN-05). The Deployments tab (`SkillDeploymentsTab`) and the bulk-deploy sheet filter on `installedPlatforms()`; tests inject a stub probe so detection is host-independent.

**Categories: a standing-rule fan-out reconciled to disk** (PLAN-06). A `Category` `@Model` (`Pensieve/Models/Category.swift`) is a persistent grouping + standing rule: it owns member projects (`projectKeys: [String]` of `Project.identityKey`) and assigned skills (`skillSlugs: [String]` of `Skill.directoryName`) — keyed by the **cross-machine-stable identities**, never local UUIDs, so BETTER's sync serializes a category verbatim with no rework (the `Skill.tags` `[String]` precedent; no SwiftData `@Relationship`). `CategoryStore` (`Pensieve/Services/CategoryStore.swift`, `CategoryStoreProtocol`) is pure CRUD over the rule arrays plus the reconcile-aware overloads. The heart is **`CategoryReconciler`** (`Pensieve/Services/CategoryReconciler.swift`, `CategoryReconcilerProtocol`): a convergent desired-vs-current engine that computes the desired set of `(skill, project, agent)` deployments declared by the rules (across `deployablePlatforms(forProject: true)`), diffs it against the **realized per-agent ledger** (`SkillProjectAssignment`, reshaped into one row per `(skillID, projectID, platform)`), and drives `PlatformViewModel.deployBatch`/`removeBatch` to close the gap — ledgering only the agents that actually deployed (a failed agent retries next run; a failed unlink keeps its row). **Critically, the reconciler constructs no path and does no file I/O** — it passes `Skill`/`Project` *objects* to `PlatformViewModel`, so the entire fan-out write surface stays inside the already-reviewed `LinkService`/`CursorCompiler` chokepoint (§2 boundary preserved at scale). Category changes are **destructive by design**: un-assigning a skill, deleting a category, removing a project from a category, or deleting a referenced skill reconciles the managed symlinks **off** the user's project directories (rules govern files) — in deliberate contrast to PLAN-05's non-destructive project-unregister. Entity deletion follows the mandatory order **prune rule keys → reconcile while the entity is live → delete the record (only on a clean reconcile)**, so no orphaned symlink is left with its referencing entity gone and no retry path. A skill's deletion is the exception: `SkillDeletionFlow` removes every deploy of the skill first, then retires its intents, its ledger rows and its category memberships, and keeps the skill if any removal fails. The Categories `SidebarSection` opens `CategoryListView`; its `EntitySelection` opens `CategoryDetailView` for membership and assignment toggles. The pure `contentColumn` and `detailColumn` functions enforce that section-to-entity route.

**Legacy scenario handover.** `ScenarioHandover` runs once per Mac during launch ingest, under the launch lock and before convergence. It writes representable legacy pairs with a safe store folder as this Mac's user-wide intent in one manifest update, then saves ownership and retires the scenario rows in separate saves. Only working deploys receive a realized `IntentAssignment`: a symlink resolving to this skill's existing store folder, or a regular Cursor file matching its compiler output. Intent reconciliation deploys unrealized pairs after handover. Handover retires the scenario ownership of a skill with no safe store folder, logs it and records no new intent. If every intent is already durable, handover skips the manifest write. A successful write nudges sync once, including when a later save fails. Handover clears the active reference and marks completion after retirement. Failed migration writes, rebuild saves or unfinished ingestion defer handover; migration still runs under the launch lock when ingestion needs a retry. An unrepresentable slug stays deployed as an unmanaged file and is logged. Existing agent files stay untouched. `IntentReconciler` honors leftover scenario ownership until completion.

The SwiftData container retains `Scenario` and `ScenarioAssignment` for compatibility and handover. No feature reads or edits scenario definitions. The schema-v5 manifest reader ignores `manifest/scenarios/`. Every `ManifestService.write` call shares one process lock. The atomic writer carries regular entries byte for byte through FileService's no-follow directory descriptor, in bounded chunks, and keeps an empty folder for older builds. It snapshots identities, file types, sizes and modification times, checks them after copying and again immediately before the swap, and aborts on replacement, changed bytes or entry additions/removals. Permission changes, xattrs and additional hard links leave byte freshness unchanged. Listing, copy or validation failures preserve the live manifest for a later retry. Callers retain their existing `sync.lock` ownership.

## 3. Data flow

**Create a skill:** `SkillLibraryViewModel.createSkill(...)` → `SkillStore.createSkill(name, description, body)` slugifies the name (hardened non-empty), ensures a unique dir, and writes a **self-describing** `SKILL.md` (composed `name`+`description` YAML frontmatter + body; description falls back to the name when none is given) → a `Skill` is inserted into the passed `ModelContext` and saved → the manifest overlay is regenerated (continuous currency). Body+frontmatter on disk, metadata in SwiftData, overlay on disk, in that order.

**Deploy:** `PlatformViewModel.deploy(skill, platform, projectPath, context)` → for a symlink platform `LinkService.link` creates the symlink (`~/.claude/skills/{dir}/` → `~/.pensieve/skills/{dir}/`, or `{project}/agents/{dir}.md` → `.../SKILL.md`); for Cursor `CursorCompiler.compile` regenerates the `.mdc` → a historical `DeployRecord` is inserted and the per-machine `DeployStateStore` records the current artifact path when project identity is available. `PlatformViewModel.refreshCounter` is bumped so the detail's snapshot re-reads `isDeployed` for every platform and project (filesystem reads, off the render path).

**Import (first run / wizard):** `ImportScanner.scan()` walks `~/.claude/skills/*/SKILL.md`, `~/.grok/skills/*/SKILL.md`, and `~/.cursor/rules/*.mdc`, skipping any Claude or Grok path that is already a symlink into `.pensieve` (already managed). Codex's user-wide `~/.codex/skills/` is scanned like the others, its `.system` entry skipped (PLAN-30). Word-set Jaccard similarity > 0.8 flags duplicates. Local import drops a leading UTF-8 byte-order mark before parsing. `ImportViewModel.importSelected` keeps the remaining local `SKILL.md`: it sets name and description in preservable frontmatter and retains the other bytes. If fenced frontmatter cannot be preserved safely, a fresh two-key header wraps the entire source as body and the result names the skill whose frontmatter was kept as text. Body-only sources receive the same header. Discovery admits only a regular-file leaf and reads through a no-follow descriptor; a symlinked skill folder outside the store remains supported. Cursor `.mdc` rules retain their existing two-key composition. SwiftData rows and the manifest carry normalized source tags while a source `tags:` entry stays as authored (PLAN-42).

**Install or adopt from GitHub (PLAN-19):** `SkillInstallViewModel` parses a pasted URL through `SkillInstallURL`, then `SkillInstallService.fetch` shallow-clones the reconstructed remote and returns bounded discovery candidates. The user selects candidates; install copies the full regular-file subtree to an out-of-store same-volume staging directory, atomically swaps the canonical destination under `sync.lock`, upserts schema-v3 provenance, and inserts the SwiftData row. A collision can rename, skip, or adopt. Adopt writes provenance and reports drift but never changes the existing canonical bytes.

**The upstream History read (PLAN-35/39).** An installed skill's History tab reads its origin repository on demand and keeps no clone. `UpstreamHistoryService` validates the stored coordinates before any subprocess — `InstallRemotePolicy` for the remote, `InstallRelativePathPolicy` for the path (shared with install, so install tightened too), Git's ref-name rules for the ref — then runs a bounded scratch fetch (200 repository commits per window, 20 path rows, 256 KiB per text file, an aggregate baseline cap) through `GitService+UpstreamHistory*` with the install credential isolated the same way `UpdateCheckService` isolates it; rows and the installed position share one first-parent-diff rule; every stored path is a `:(literal)` pathspec; the scratch directory dies with the read and a launch sweep removes crash residue. It returns rows, the installed position as a tri-state, each row's `SKILL.md` text, and the installed baseline that `UpstreamHistoryService+LocalEdits` measures the working copy against. The widest validated parsed result for each skill is kept under the runtime's Application Support directory; this disposable cache contains no git state and never enters the store or manifest. `UpstreamHistoryViewModel` shows a matching kept result before doing network work and re-measures local edits from its baseline. It refreshes only when the recorded head moved, the first head probe for that skill in this launch finds a different head, or the user asks. The History service admits and reconstructs the probe exactly like a read and uses the same install credential isolation. Kept rows stay visible while a refresh or wider read runs and after a refresh failure. A saved local edit recomputes only the edits, a wider window replaces a narrower one, and a view's ask carries its intent (`appearance`, `retry`, `mountedRefresh`) rather than being inferred from revision equality. `InstalledSkillHistoryView` with `InstalledSkillHistoryPresentation` renders the timeline, inert diff sheets (CONVENTIONS §14), and `Update to This`, which hands off to Skill Updates — the one apply path; it never writes update-check state, and authored or imported skills keep the sync-repository History.

History requests for one skill go through one flow value and one reducer (`UpstreamHistoryFlow`, `UpstreamHistoryViewModel+Flow`). The value owns kept results and failures, requests and operation waiters, a retained probe answer, and manual-check state. A request at a new origin prunes the old origin’s state and retires its job identities. Workers can still finish, but retired outcomes are ignored. A disk answer can widen memory at the same read head; it cannot displace a different head already in memory. One helper resolves the read head answering a question across all held windows; its memory-only certifications survive replacement by wider rows. Disk loads, reads, probes, local measurements and persistence return tagged completion events. The reducer admits each registered outcome once and selects its current waiter by request identity before publishing or starting follow-up work. Read completion records the waiter it advanced on the persist job; persistence uses that recorded decision even if held rows change. Superseded requests can still finish owned work without publishing for another question. Exact joins with kept rows can return immediately; closing a view does not retire its question or cancel model-owned work. A probe completed while another question is current stays available for one later decision. Removal drops the flow and fences disk generations. Only a newly started read spends a manual ask; a current waiter that joined older work performs that read after the older outcome arrives. The view observes the manual-check revision rather than internal flow mutations. The test seam records every publication decision, while equal visible states do not trigger an observed assignment. Service operations remain synchronous and run in detached tasks; local measurements and persistence use utility priority.

**Check and apply skill updates (PLAN-19):** a manual or due foreground check calls `UpdateCheckService`, which batches linked skills by repository/ref and writes only local SwiftData flags and pinned upstream coordinates. The updates notice opens `UpdatesViewModel`: View Changes re-fetches and verifies the displayed commit/tree before reading upstream `SKILL.md`; Apply repeats the pin check, requires explicit confirmation for local drift, then calls the atomic update path to replace the complete vendored directory and refresh `InstalledOrigin`. One row failure does not abort the batch. No update is installed automatically.

**Register a project (PLAN-05):** `AddProjectSheet` picks a directory; the live identity preview calls `ProjectIdentityService.peekIdentity` (read-only). On "Add", the pure `ProjectRegistration.makeProject(name:path:using:)` factory builds a `Project`, computes its identity via `identity(forProjectAt:)` (the write path — creating a `.pensieve-project` marker for a non-git dir), stamps `identityKey`/`identityKind`, and the row is inserted. The Projects `SidebarSection` opens `ProjectListView` in the content column, where registered projects are sorted by name and carry a monochrome identity-kind indicator (`arrow.triangle.branch` for a git remote, `tag` for a marker). Its context-menu "Remove" deletes only the `Project` record (registration-only, never the directory); selecting its `EntitySelection` opens `ProjectDetailView`.

**Content — rendered and source:** the Content tab's rendered view and editor read `SkillLibraryViewModel.readBody`, which runs `SkillParser.stripFrontmatter` over the raw file (see §4 — frontmatter on disk is real and canonical). A body save re-reads and parses the file, then writes through `SkillStore.rewriteSkill`, which splices the new body into the file's own bytes — frontmatter keys Pensieve does not own, fences, spacing, and the trailing-newline state stay exactly as written — and a metadata edit regenerates the manifest overlay; `Skill.updatedAt` is bumped manually (SwiftData does not auto-touch it). The editor's text is a draft on the view model (`drafts`, keyed by slug) until Save: `noteEditorChanged` opens an entry at the first differing keystroke and closes it on a return to the file's text, dirty is measured against the fingerprint (so a file that catches up reads clean without the entry going), `saveDraft` writes it through `updateBody` and re-seeds the fingerprint, `discardDraft` drops it, and `confirmLeaving` is the one gate every way out of an edited skill passes — the view model, not a view, decides what an external change does to a dirty editor (ask, never reload). The detail's snapshot (`DetailContentSnapshot`) also carries the skill directory's inventory (`SkillBundleInventory`, PLAN-34) and the deploy status of every installed platform for This Mac and each registered project, all read in the loader. The loader re-runs on the skill, an external change, an app write, a deploy change, a project change, and every watcher event — a change to a bundle file other than `SKILL.md` reaches the app only as an event the body check calls an echo; the Content tab's other-file text is re-read on the same signals. The detail is one header over tabs (`DetailTab`, `Views/SkillViews/Detail/`); the tab switch, the file pulldown, and the rendered toggle are ways out that pass `confirmLeaving`; Delete asks its confirmation alone. History is the tab's timeline over `GitService.log` (`SkillHistorySnapshot`, read when the tab is shown); Restore confirms and writes through `restoreSkillHistoryVersion`, which drops a draft only after the write; the sheet remains the conflict flow's.

**Rebuild / migrate (PLAN-07 + PLAN-12 launch catch-up):** on launch `LaunchReconciler.reconcileOnLaunch` first tries to rebuild SwiftData from the file store when the manifest is authoritative/readable enough to consume, before the watcher starts and before any manifest write. `StoreRebuildService.rebuild(fromRoot:context:)` reads the manifest once, admits only skills whose `SKILL.md` has required frontmatter (skip + warn otherwise), and converges SwiftData's `Skill`, `Category`, and `MachineDeployIntent` rows to disk + overlay (insert/update/delete, idempotent). It retries once if `.git/HEAD` advanced mid-rebuild, so a daemon fast-forward that lands during launch gets one bounded re-read. When the rebuild bails `storeUnreadable` (a newer schema or a corrupt file), the outcome fences every add through `SkillLibraryViewModel.addsFenced` — until a sync cycle gets past the engine's pre-write read (`.synced` or `.conflicted`) or a relaunch reads the manifest; edits stay open. Only after a clean rebuild does the one-time `StoreMigrationService.migrateIfNeeded` backfill not-yet-self-describing owned skills (frontmatter + overlay); that migration write is skipped when `sync.lock` is busy or HEAD moved since the rebuild, and the marker persists only on all-clear. Neither path invents a path-less `Project`: a synced project *identity* with no locally-registered `Project` simply doesn't fan out.

**Category assignment / reconcile (PLAN-06):** a toggle in `CategoryDetailView` (or a sidebar category CRUD action) calls `CategoryStore.setSkill`/`setProject`/`delete(...reconciler:)`, which mutates the rule arrays and then calls `CategoryReconciler.reconcile(context:)`. The reconciler resolves the stable keys to live `Skill`/`Project` objects (skipping any dangling id), computes desired-vs-current `(skill, project, platform)` triples, and drives `PlatformViewModel.deployBatch`/`removeBatch` per `(skill, project)` group — inserting a `SkillProjectAssignment` ledger row per *successful* deploy and deleting one per *successful* unlink. The returned `BatchResult` surfaces successes quietly and failures in the §5 (`BulkDeploySheet`) tone.

**Resident sync and convergence (PLAN-23):** the scheduler hands one trigger to `SyncCoordinator`, which opens a fresh context and calls `SyncEngine.sync(...prepare:)` from detached actor work. Under the engine-owned `sync.lock`, `prepare` rebuilds if the last ingested HEAD is stale or unknown, then publishes this machine's state file. The engine snapshots, commits, pulls/rebases, rebuilds, and pushes. On success, `PostSyncConvergence` runs deploy self-healing; when the cycle ingested a new HEAD it also runs category and intent reconciliation in order on a new main-actor context. A conflict runs none of those effects and remains in the existing resolution flow.

**Machine deploy intent (PLAN-23/36):** in user-wide mode, `BulkDeploySheet` gives each skill/agent choice a machine multi-select. In project mode it writes project-scoped intent for This Mac. `DeployIntentModel` replaces the selected rows in SwiftData, writes schema-v5 per-entry files, saves, nudges sync once, and invokes the local intent reconciler. A This Mac selection can realize immediately. An apply that changes the selection's rows then runs the local intent reconciler, so an apply that drops This Mac retracts its intent and removes the deploy that intent owned. An apply that changes no rows skips that reconcile unless This Mac is selected. A remote-only selection adds no local deploy of its own. The Deployments tab's remote switches take a persistence-only path instead: they write the addressed intent, nudge sync, and run no local reconcile. Retraction deletes the per-entry fact. One file can also carry project-scoped entries, addressed by the project's cross-machine identity key and a platform list. `IntentReconciler` considers this machine's user-wide and project rows for locally installed platforms, resolves slugs and registered project identities to local rows, and diffs desired pairs or triples against `IntentAssignment`. It sends all file effects through `PlatformViewModel`; failed removals stay ledgered for retry, another owner's deploy survives, and unledgered manual deploys survive until a matching intent adopts them.

**Machine observation (PLAN-23/36):** `MachineIdentity` reads or creates the canonical UUID in app support. During `prepare`, `MachineStateService` composes detected agents, stable project identities with optional display-only home-abbreviated paths, and realized `deploy-state.json` records, then atomically replaces only `machines/<own-id>.yaml` when its content changed. `ContentView` tolerantly reads those state files after launch and sync-state changes. The Machines `SidebarSection`, its `MachineListView` content, and each `EntitySelection` detail are read-only; remote-only projects never become local `Project` rows.

**Where state lives:** `AppRuntime.makeContainer` defines the SwiftData schema for skill/project metadata, historical deploy records, categories, `MachineDeployIntent`, and the local category and intent assignment ledgers. Settings are `@AppStorage` / `UserDefaults`, including the handover completion marker, machine display name, and background-sync preference. The canonical body, schema-v5 manifest overlay, `machines/` state, and deploy artifacts are on the filesystem. `machine-id`, SwiftData, audit files, and `deploy-state.json` stay under app support; sync credentials live in the macOS Keychain (`KeychainCredentialStore`) and settings in `UserDefaults` — all machine-private, none of it synced.

## 4. Cross-cutting concerns

**Error handling.** Error typing is **uneven** today: the git, sync, install, and update services define typed `LocalizedError` enums (`LinkError`, `GitError`, `SyncError`, `CredentialError`, `SkillInstallError`, `SkillUpdateFlowError`, `UpdateCheckError`, `MachineStateError`, `SkillInstallURLParseError`); `SkillStore` throws a plain `SkillStoreError: Error`; `FileService` propagates Foundation/`NSError` directly. View models `catch` whatever propagates and surface a `String?` `error` for the UI. Parsers degrade rather than throw. `SkillParser.parse` returns an all-body `ParsedSkill` when the YAML frontmatter is absent or unparseable. PLAN-07 read it through Yams. PLAN-38 now checks it before construction. Admission is gated separately by `hasRequiredFrontmatter`, not by "did it parse." No silent empty-catches in services — a manifest-regeneration or store-save failure is surfaced (a warning or the view model's `error`), never swallowed by an empty `try?` (the recurring PLAN-07 review rule). (Standardizing on typed service errors is a reasonable future convention — not yet reality.)

**Frontmatter on disk is now intentional and canonical (PLAN-07).** Before PLAN-07 the store was *intended* to be clean body-only markdown and any frontmatter was merely hidden at read time. That is **reversed**: an owned `SKILL.md` **is** a self-describing file — YAML `name`+`description` frontmatter + body. Pensieve composes that canonical file only when it creates one: `SkillStore.createSkill` for authored skills and Cursor rules, and local import when a source's frontmatter can't be preserved, which puts the whole source under a fresh two-key header (`ImportViewModel`, PLAN-42). A local import whose frontmatter can be preserved is written with only `name` and `description` spliced, and import checks the result before writing it; an edit-save goes through `SkillStore.rewriteSkill` and replaces only the body, and the store migration normalizes `name` and `description` by splicing just those two entries, leaving a file it cannot split safely unchanged with a warning (PLAN-37 — the old save re-emitted exactly two keys and dropped the rest, `license:` included). The editor still hides frontmatter at *read* time (`readBody` → `SkillParser.stripFrontmatter`) and the self-write fingerprint is computed on the *stripped* body, so the editor UX is unchanged while the on-disk file gains frontmatter. The **tolerant vs. required** distinction is load-bearing: `SkillParser.parse` tolerantly reads whatever frontmatter is present (missing keys → nil), but a separate `ParsedSkill.hasRequiredFrontmatter` (both `name` and `description` present + non-empty) is the gate at import preservation, migration, and rebuild admission — a body-only file *parses* (as all-body) but is **not** an admissible skill.

**Hashing / freshness.** Cursor freshness (`CursorCompiler.isUpToDate`) compares the full regenerated `.mdc` against the file on disk. `DeployRecord.contentHash` and `FileService.contentsHash` still use Swift's process-seeded `Hasher` and must not be treated as cross-launch or cross-machine signals. GitHub-installed skills use a separate stable SHA-256 tree hash from `SkillInstallService`: entry-counted fixed-width path/content digests plus owner-executable mode, in byte-sorted path order. `InstalledOrigin.contentHash` records that value for local-drift checks; `installedTree` remains the git-native upstream-change signal.

**Concurrency.** Leaf services remain synchronous and throwing. Resident orchestration is the narrow async layer: `AppRuntime` and `SyncScheduler` are main-actor-owned, `SyncCoordinator` is a `@ModelActor`, and runtime entry uses detached tasks so synchronous git and SwiftData work stays off the main actor. Each coordinator cycle and each ledger convergence pass uses a fresh context. Swift 5.10 strict concurrency remains off; do not invent async seams below this orchestration boundary (see `docs/CONVENTIONS.md` §7).

**Security posture.** The app is **unsandboxed by design** (`ENABLE_APP_SANDBOX: NO`) — it needs to write symlinks across `~/.claude`, `~/.grok`, `~/.codex`, `~/.openclaw`, `~/.hermes`, `~/.cursor`, and arbitrary project dirs the user registers. Public releases are signed and notarized through PLAN-18; signing and publishing remain human-gated. The app reads and writes files in the user's real agent directories, so a path-construction bug has real blast radius — this is why `Constants` centralizes paths, `FileService` is the single chokepoint, and `LinkService.validatePathComponent` rejects an escaping `Skill.directoryName` or category (`.`/`..`/`/`/leading-`~`) before any symlink is created or removed (PLAN-04). A PLAN-04 `/security-review` over the new path/symlink surface found no exploitable traversal. PLAN-06's category reconciler deploys/removes across *many* `(skill × project × agent)` tuples in a loop, but every write still routes through `PlatformViewModel.deployBatch`/`removeBatch` → `LinkService`/`CursorCompiler`: the reconciler builds **no** path and does **no** file I/O (it passes `Skill`/`Project` objects), category rule strings (`projectKeys`/`skillSlugs`/name) are only lookup keys never path components, dangling ids are skipped, and the destructive reconcile removes only link *entries* within chosen project dirs (`removeItem(atPath:)` does not follow symlinks). A PLAN-06 `/security-review` over the fan-out write surface found no exploitable traversal (06.6-a). PLAN-07 adds one new untrusted-input surface — parsing **third-party YAML frontmatter** — handled by **Yams** (the same LibYAML-backed parser SwiftLint trusts for arbitrary `.swiftlint.yml`); parsed frontmatter values are read as data (`name`/`description`) and **never** used to construct a filesystem path or a shell argument. The manifest's one free-string→filename surface (category names) is encoded only through the safe `ManifestService.categoryFileName` (`slugify` strips `/`, `.`, and every non-`[a-z0-9-]` char, then a SHA-256 suffix), so a crafted category name cannot escape `manifest/categories/` (the §A filename tests are the executable teeth). A PLAN-07 `/security-review` over the Yams + manifest-filename surface found no exploitable path (07.6-e). PLAN-38 later replaced direct Yams reads with `CheckedYAMLLoader`, which validates LibYAML events before Yams constructs values. **PLAN-08 adds three untrusted-input surfaces — the git subprocess, HTTPS-PAT credential handling, and content pulled from a remote — all reviewed clean at 08.5-a** (see §2 "The sync layer"): the subprocess passes args as an array with `--` option terminators (no shell, no git-option injection), `parseRemote` rejects `ext::`/`fd::` remote-helper syntax that git would *execute* plus https-userinfo, the PAT never reaches argv/`.git/config`/disk and the Keychain query is namespaced so a delete can't wipe a foreign credential, and `StoreRebuildService` performs **no filesystem write derived from remote-controlled names** (it reads `skills/<slug>/SKILL.md` and writes only to SwiftData; the only manifest writes go through the sha256-safe `categoryFileName`). The structural teeth (args-as-array grep, no-`/bin/sh` grep, no-token-`writeFile` grep) are the executable checks in the 08.5-a Verify block. **PLAN-10 (BETTER-2 prelude) hardened all of the above — the deferred PLAN-08/09 review residuals — and passed `/security-review` clean over the whole branch (10.7):** the remote-admission policy moved into a single `RemoteURLPolicy` shared by connect (`SyncSetupModel.parseRemote`) and a new **sync-time re-validation** (`SyncEngine` re-checks the stored `.git/config` `origin` through the same policy before *every* network op — closing the "stored origin weaker than connect" gap), extended to reject interior newlines and to parse bracketed IPv6 hosts; `GitService.childEnvironment` now **strips the full inherited git-behavior-override family** (`GIT_SSH*`/`GIT_PROXY_COMMAND`/`GIT_EXTERNAL_DIFF`/`GIT_CONFIG*` + indexed keys/`GIT_ALTERNATE_OBJECT_DIRECTORIES`/`GIT_NAMESPACE`/`GIT_TRACE*`) while deliberately preserving the hardening `GIT_CONFIG_NOSYSTEM`, and the HTTPS token rides only the child env (never argv, the on-disk askpass-helper body, or `.git/config`; a helper-write failure now *propagates* instead of proceeding unauthenticated); `conflictedFiles` enumerates with `-z` (NUL-delimited), so an embedded-newline conflicted path is one exact entry instead of two fragments; the **manifest reader strict-shape-validates the list-shaped membership fields** (`project_keys`/`skill_slugs`/`tags`/`agents`) — present-but-not-a-sequence throws `corruptManifestFile`, fail-safe end-to-end (read throws → `StoreRebuildService.rebuild` bails mutating nothing → `SyncEngine.sync`'s pre-write read guard aborts before emptying or pushing) while additive scalars stay tolerant for forward-compat; and a **total canonical-store slug-dir guard** now holds — *Pensieve never reads, writes, or deploys through a symlinked `skills/<slug>` dir*, enforced at every sink (`SkillStore.readBody`/`createSkill`/`rewriteSkill`/`writeBody` via `validatedSkillDirectory`, `PlatformViewModel.deployOne`, `StoreMigrationService`, `StoreRebuildService` skip-with-warning preserving the row, `Skill.estimatedTokens`→0, and `SyncEngine.validatedWorktreePath`'s rejection of a symlinked non-leaf component; a symlinked *leaf* stays safe because atomic write replaces the link). PLAN-10's `/security-review` over this combined remote-URL / credential / symlink / manifest surface found no exploitable path (10.7). **PLAN-11 (BETTER-2) then consolidated that slug-dir guard into one primitive:** the five formerly-open-coded checks above — the three `SkillStore` body sinks (via the throwing `validatedSkillDirectory` wrapper), `PlatformViewModel.deployOne`, `Skill.estimatedTokens`, `StoreRebuildService`, and `StoreMigrationService` — now all route through a single reviewed **pure resolver `SkillStore.safeSkillDirectory(slug:base:fileService:) -> String?`** (returns `<base>/<slug>`, or `nil` for an empty/`/`/`.`/`..` slug or a symlinked/realpath-escaping dir). It carries the strongest form — component validation + symlink rejection + realpath-containment — *uniformly*, so the four sinks that previously open-coded a weaker `isSymlink`-only check are **leveled up** to it (they now also reject `..`/`/`/`.`/empty), and a sixth sink cannot bypass the invariant without visibly *not* calling the shared function. Each caller keeps its own control flow around the `nil` (deploy throws, token count returns 0, rebuild/migrate skip-and-preserve the row + warn — never throw, so the PLAN-08 row-wipe fail-safe is intact) — a **pure resolver, not a bare `throws`**, exactly so the fail-safe skip sinks need not catch. `SyncEngine.validatedWorktreePath` remains **separate** — it validates arbitrary multi-component git-relative paths with leaf-vs-non-leaf symlink semantics (a superset problem), not a single canonical slug, and is deliberately not folded in. This is defense-in-depth + anti-drift, not a bug fix (PLAN-10 confirmed all five sinks were already guarded); PLAN-11's `/security-review` over the consolidated guard found no exploitable path (11.3), and PLAN-12's daemon inherited `safeSkillDirectory` as the single call for any canonical slug path it touches.

PLAN-23 adds the synced deploy-intent control channel. Exact-canonical machine IDs and restricted slug/platform components are admitted before path construction; the parser refuses a wrong shape, a key mismatch or a bad component as a corrupt file, and the writer accepts only admitted components; `IntentReconciler` resolves only local skill rows and routes effects through the existing deploy sinks; per-entry files keep retraction out of union-merge semantics; and no new network operation bypasses `RemoteURLPolicy`. The PLAN-23 security review found no qualifying vulnerability across those bounds. PLAN-36 extends that accepted authority from agent home directories to the projects this Mac has registered: `IntentReconciler` also resolves project entries, but only to registered local projects, so someone with write access to the sync repository can cause Pensieve's own skill links to appear inside those projects, never in any other folder. Project keys are always written double-quoted. PLAN-38 makes `CheckedYAMLLoader` the one way Pensieve reads YAML, including the serializer's bare-scalar quoting oracle. It validates libyaml events before Yams composition or construction. It refuses a non-scalar mapping key, an explicit merge tag on a mapping key, nesting deeper than 64 total constructed levels including depth reached through aliases, merge nesting deeper than four levels including mappings reached through aliases or as merge-sequence items, and any node tag longer than 256 UTF-8 bytes either before or after repairing malformed UTF-8, whether written directly or expanded from a `%TAG` directive. The validator considers implicit merge spelling for every implicit scalar. A constant-time byte comparison matches Yams' merge regex: exactly `<<`, optionally followed by one final LF, VT, FF, CR, CRLF, NEL, LS or PS. Untagged scalars must still be plain, while an empty reported tag remains implicit in any scalar style. The same resolver instance is passed to every Yams construction call. It is module-internal, the narrowest visibility that lets the `@testable` target compare the byte classifier with the resolver actually in use. The suite audits this boundary in ordinary code with `CheckedYAMLLoaderTests.testAppYAMLReadsUseCheckedLoader`, which applies PLAN-38 criterion 38.2-e's load, compose, decoder, constructor and node-value patterns, widened to unqualified stream calls, whitespace and line breaks within calls, Yams `Parser` type references and `CYaml` references, to Swift sources under `Pensieve/` except `Pensieve/Services/CheckedYAMLLoader.swift`. Yams import detection covers attributes, declaration kinds, indentation and line breaks; CYaml token matching also catches imports with intervening comments. This is a textual audit, not a defense against deliberately hidden calls: `import /* x */ Yams` is not recognized as a Yams import. Alias expansion has a 100,000-unit cost budget. Each alias is charged once for its expanded subtree: one unit per repeated node, each scalar's UTF-8 bytes, and the full resolved-tag bytes. Implicit and non-specific scalars conservatively cost the longest tag Yams can resolve, a constant 27 bytes. An empty reported tag is normalized to implicit and receives that same charge. Explicit tags cost their decoded bytes. Implicit containers cost their resolved `seq` or `map` tag bytes. Alias-free literal data consumes no alias budget, but remains subject to the tag and merge-nesting caps. Its checked integer constructor makes an overflowing sexagesimal integer load as its string. Each reader maps a refusal to its existing parse-failure behavior, so manifest and sync reads fail closed, machine state is skipped with its warning, and skill frontmatter becomes the existing all-body fallback. For writing, the loader reports a bare scalar's constructed value and whether construction used the integer-overflow string fallback. The writer quotes a scalar that does not construct as the identical string. It also quotes the overflowing sexagesimal integer whose checked construction falls back to a string, because an older build's plain Yams constructor would trap. Other resolved tags that already construct as strings retain their legacy bare bytes. The writer escapes U+FFFE and U+FFFF because libyaml refuses either raw even inside a double-quoted scalar.

## 5. Extension points

- **New agent/platform** → add a `PlatformTarget` case, its `Constants` paths, and (if it reads standard `SKILL.md`) route it through `LinkService`'s symlink branch; `AgentDetectionService` gates whether the UI shows it. A non-standard format gets its own compiler alongside `CursorCompiler`. (PLAN-04 added OpenClaw + Hermes this way, and PLAN-22 added Grok; a generic custom-agent adapter is deferred — see PLAN-04 non-goals.)
- **New import source** → legacy/local scanners add a `scanX()` to `ImportScanner` returning `DiscoveredSkill`s. A network or registry source should normalize into `SkillCandidate`/`SkillFetchResult` and feed `SkillInstallService`, preserving the same vendor/provenance/update boundary. GitHub is the only shipped remote source; registry browsing, archives, `.cursorrules`, and `AGENTS.md` remain future.
- **Per-category agent selection** → an additive refinement of PLAN-06's category fan-out: because the `SkillProjectAssignment` ledger is already per-agent, a category-level platform preference can narrow the *desired* set without changing the realized row shape (promote `skillSlugs` to a join carrying `[PlatformTarget]`). Today a category assignment fans out to *all* project-capable installed agents.
- **Cross-machine control** extends the shipped resident convergence layer. Deploy intent is machine-scoped and can address the whole Mac or a stable `Project.identityKey`; `IntentReconciler` maps project entries to every matching registered local project and records each realized artifact in its project-aware ledger. Category fan-out remains a separate owner that composes with project intent. Any extension must preserve per-entry retraction, exact-canonical machine admission, locally resolved paths, and the existing deploy sinks.
- **MCP server / CLI (BEST-3)** sit beside the view layer: another caller of the same services. Keep business logic in services, not view models, so a non-GUI front end can reuse it.

## 6. Conflict resolution (PLAN-09)

When `SyncEngine.sync` hits a body/overlay conflict it aborts the rebase and returns `.conflicted([paths])` — a **safe resting state**: our commit is unpushed, `origin/main` is still divergent, the working tree is clean, no rebase is in progress (PLAN-08's interim). PLAN-09 resolves that seam with a **reproduce-conflict**-on-demand model: the conflict is never persisted mid-rebase; it is re-derived on demand through a shared prelude (`prepareLocalHead` — write the manifest snapshot + install union attributes + a **single-commit collapse** of unpushed divergence, so `pull --rebase` always replays exactly one commit) followed by `pullRebase`.

- **`SyncEngine.inspectConflicts`** reproduces the conflict, reads both sides, and aborts back to the safe resting state — returning a `ConflictSet` of correctly-labeled items (or `.cleared` if the conflict resolved itself upstream).
- **`SyncEngine.resolveConflicts`** reproduces the conflict, verifies it is unchanged (the reproduced blobs still equal what the user saw — else `SyncError.conflictsChanged`, and the UI re-inspects), writes the picked side through the path-guarded `validatedWorktreePath` sink, `rebase --continue`s (with a proven-empty `--skip` for an emptied "keep other"), rebuilds, and pushes. Any failure aborts the rebase back to the safe resting state.
- **⚠️ The rebase stage mapping — opposite of a plain merge.** During `git pull --rebase origin main`, **`stage 2` = `origin/main` = the OTHER machine**, and **`stage 3` = the replayed local commit = THIS machine**. `inspectConflicts`/`resolveConflicts` read `:2:`/`:3:` accordingly; inverting this labels every diff side backwards.

The diff and version-history views render this pulled/replayed content **inert** (CONVENTIONS §14). The reproduce-conflict engine, the value types (`ConflictSet`/`ConflictItem`/`ResolutionPick`/`ConflictInspection`), and the `GitService` conflict/history primitives are reusable by BETTER-2's headless/daemon path.
