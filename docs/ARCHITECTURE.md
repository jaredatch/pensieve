# ARCHITECTURE.md — Pensieve

The durable shape of the system: layers, boundaries, and the key abstractions the Executor must respect. The Planner keeps this current; the Executor treats the boundaries here as load-bearing (the Never list forbids bypassing them). It is reverse-engineered from the code and documents *what is*, only where an agent could otherwise get it wrong.

## 1. Layers

Four layers. Leaf dependencies point downward. Reconcilers orchestrate deployment through `PlatformViewModel` (`CategoryReconciler`, `IntentReconciler` and `WaitingRemovalReconciler`); this is the orchestration exception to that direction. Views never touch the filesystem or `FileManager`; services never import SwiftUI (one exception: `SyncScheduler` imports it for its `@AppStorage`-backed background-sync preference).

```
Views (SwiftUI + named   Pensieve/Views/**        presentation only; @Query, @Bindable, @Environment(\.modelContext)
       AppKit bridges)
   │
   ▼
ViewModels (@Observable)  Pensieve/ViewModels/**    UI state + intents; hold service protocols; take a ModelContext per call
   │
   ▼
Services (protocols)      Pensieve/Services/**       all business logic + the only code that talks to the filesystem
   │
   ▼
Models (@Model) + FS      Pensieve/Models/**         SwiftData metadata  +  ~/.pensieve/skills/{dir}/SKILL.md body
```

Beside the layers: `AppRuntime` (`Pensieve/AppRuntime.swift`, process-scoped; §2 "The resident runtime") owns the `ModelContainer` and the long-lived view models and services, and `Pensieve/Utilities/` holds the SwiftUI-free helpers shared across layers (`PathConstants`/`Constants` paths, `DeployIndex`, `ListRows`, `AppSignal`, `RelativeTime`, `GitHeadStamp`, `DogfoodMode`).

**The view layer is SwiftUI everywhere except eight named AppKit bridges.** Each is a narrow first-party hosting adapter, not private-view introspection, and new AppKit use needs the same justification (use the AppKit control only where a SwiftUI wrapper visibly diverges from the tier-1 pattern):

- **The sidebar** is an `NSOutlineView` in `.sourceList` style, hosted by the `NSViewRepresentable` `SidebarOutline` (`Views/MainWindow/SidebarOutline.swift`; `SidebarOutlineController` is its data source/delegate). `SidebarRows.items(showsMachines:)` builds the static section list and hands it to the outline; the selection binding is written only from a user selection.
- **The tag editor** is an `NSTokenField` hosted by the `NSViewRepresentable` `TagTokenField` (`Views/SkillViews/TagTokenField.swift`); its coordinator owns the editing baseline and completion. SwiftUI has no token field, so Pensieve uses the AppKit control.
- **The editor** is the vendored CodeMirror running in a hardened `WKWebView`, hosted by `MarkdownEditorWebView` (`Views/SkillViews/Editor/`). Canonical skill bodies — a sync pull's included — reach it through `readBody` and the marshalled bridge; conflict sides, diffs, and past versions render inert and never enter it (CONVENTIONS §14).
- **Skill export** uses `NSSavePanel` in `SkillExportPanel` for the filename, folder creation, and replacement confirmation. `SkillExportModel` reads bytes through the library’s `SkillStore` and writes through `FileService`. The save panel and errors attach to the main window.
- **Directory picking** uses `NSOpenPanel` in `AddProjectSheet` and in `ContentView.importFromFolder` (Import from Folder…).
- **Process lifecycle** is `PensieveAppDelegate` (`NSApplicationDelegate` via `@NSApplicationDelegateAdaptor`): it keeps the process alive after the last window closes and reopens the main window. (`SyncScheduler`, a service, also imports AppKit for `NSWorkspace.didWakeNotification`.)
- **The window's close veto** is `WindowCloseGuard` (`Views/MainWindow/WindowCloseGuard.swift`): a delegate proxy on the main window that answers `windowShouldClose` for an unsaved draft and forwards every other delegate call to SwiftUI's own delegate.
- **Update review window lifecycle** uses `ViewChangesWindowLifecycle` (`Views/InstallViews/ViewChangesWindow.swift`) to disable AppKit restoration and cancel previews on the actual window close. It observes `willClose` without replacing SwiftUI's delegate.

The `pensieve-conventions` project skill (`.claude/skills/`) encodes this as "three-layer pattern, no exceptions." Treat it as binding.

## 2. Key boundaries & abstractions

**`FileServiceProtocol` is the single filesystem chokepoint — the most load-bearing boundary in the app.** Every file read, write, symlink, hash, copy, and directory op goes through it (`Pensieve/Services/FileService.swift`). No service, view model, or view performs file *I/O* via `FileManager` directly. This is what makes the services unit-testable against temp dirs and lets sync intercept every mutation. Two narrow, allowed exceptions exist and don't count as I/O: `PathConstants` (re-exported as `Constants`) calls `FileManager.default.homeDirectoryForCurrentUser` purely to *derive* home-relative base paths, and `AddProjectSheet` uses `NSOpenPanel` to *pick* a directory (a UI affordance). Actual reads/writes of those paths still go through `FileService`. Two leaf primitives sit deliberately outside it: `GitService` (the sanctioned subprocess exception, below) and `SyncLock`, a raw-POSIX advisory-lock primitive that creates its own lock directory with `FileManager` because `FileService` models skill-tree CRUD, not file descriptors (its doc comment carries the rationale). The rule to enforce: no I/O outside `FileService`. The protocol also exposes `isExecutableFile(at:)` for agent detection and the PLAN-19 binary boundary: `readData`, descriptor-bound `copyFile`, and `isUserExecutableFile`. Those operations let install vendor arbitrary regular-file assets without following a symlinked leaf and preserve the owner-executable bit. `copyFile` writes a temporary sibling through its descriptor, then renames it over the destination after the copy succeeds. A failure leaves the destination intact. A destination symlink's target and a hard link's other names keep their bytes.

Project directory admission uses `FileServiceProtocol.requireProjectDirectory`, backed by the throwing, link-following `directoryExistsFollowingLinks` probe. A saved path must start with `/` and resolve to an existing directory. `ProjectDirectory.canAccess` rejects relative project paths before disk access. Missing paths and non-directories throw `ProjectFolderError.missing`; lookup errors throw `couldNotCheck` with the reason. Convergence, direct project deploys and Add Project use this admission. A direct LinkService or CursorCompiler deploy checks its root once before project-artifact lookups and writes. The returned `ProjectDirectory` carries that admission into the bounded writer; only FileService admission constructs it.

`FileService` runs each raw directory lookup at user-initiated priority with a two-second deadline. The bound applies per folder check, not per operation. Concurrent callers share an in-flight lookup's deadline and answer. An expired lookup makes later checks fail immediately until its worker finishes; the registry is shared across FileService instances and keeps no completed results. A timeout becomes `couldNotCheck`, so reconcilers retain rows and continue with other projects.

`writeFileInProject` and `createSymlinkInProject` create interior folders one level at a time and write the artifact without creating parents. The root and its ancestors are never created. Existing interior directories, including linked directories, are reused. A failed mkdir or artifact write with an inconclusive recheck keeps the original creating error. Leaf removal and status reads probe absolute artifact paths directly. Convergence and user un-selection admit the project folder before cleanup. Relative project paths cause no artifact removal or status/backfill lookup. Path builders retain actual paths for bookkeeping, including legacy relative paths. User-wide writers create missing parents recursively.

**The dual source of truth.** Skill *metadata* lives in SwiftData (`Skill` `@Model`); the skill *body* lives on disk at `~/.pensieve/skills/{directoryName}/SKILL.md`. The markdown body is **never** duplicated into the database. `Skill.directoryName` (the slug) is the join key between the two. `Skill.canonicalPath(skillsDirectory:)` computes the on-disk path from the caller’s store directory. This split is deliberate and is the foundation the cross-machine sync engine (BETTER) is built on: sync moves the self-describing files + a small manifest, and each machine rebuilds its SwiftData locally — never syncs the database.

**The self-describing store + the manifest overlay (PLAN-07/17/19/23/36).** `~/.pensieve` is a complete, portable, rebuildable, continuously-current source of truth: the contract the sync engine moves between machines. **(1)** PLAN-07 made an owned skill's `SKILL.md` carry standard **YAML frontmatter** with `name` + `description` (parsed by Yams, written by the canonical writer). PLAN-38 later replaced direct Yams reads with `CheckedYAMLLoader`. A GitHub-installed skill is instead vendored as its complete directory, byte-pristine, so scripts, assets, and executable mode remain faithful to upstream. Pensieve-authored and legacy-imported skills use the canonical writer; adopting an existing skill links provenance without rewriting its files. **(2)** Pensieve bookkeeping lives in the **per-entity YAML manifest overlay** under `~/.pensieve/manifest/`, outside skill bytes (`ManifestService`). Manifest schema v5 retains the schema-v3 `InstalledOrigin` block and schema-v4 deploy-intent files under `manifest/deploys/<machine-id>/<slug>.yaml`. Each file's `platforms` list is user-wide intent; an optional `projects` list carries project identity keys with their own platform lists. Category rules also live in the overlay; a project's identity is published per machine in `machines/<id>.yaml`, and `manifest/projects.yaml` is the constant `projects:` — older builds' entries still parse and union. The governing rule remains **sync durable facts, compute volatile flags locally**: update-check state and realized assignment ledgers live only in local SwiftData. Observed machine state is synced outside the manifest at `machines/<machine-id>.yaml`, where each machine writes only its own file. A project may carry a display-only, home-abbreviated path; the path is never identity or an input to file operations, and local absolute paths and secrets never enter machine state. Older readers fail safe, and the write-side schema guard prevents an older build from overwriting a parsed newer manifest.

**The rebuild/migrate triad (PLAN-07).** Three services keep disk ⟷ SwiftData convergent, all over the `FileService` + `ManifestService` boundary, **none touching git**: **`StoreRebuildService`** reconstructs SwiftData from disk + manifest — the clone-bootstrap for a fresh machine (files but an empty DB) and the post-pull refresh PLAN-08 runs. A convergent insert/update/delete reconcile that **admits only skills with required frontmatter** (`name`+`description` both non-empty; a body-only / malformed file is skipped + warned, never a degraded row), that **bails mutating nothing** when the manifest declares a `schema_version` newer than this build understands (`ManifestService.read` throws `unsupportedSchema`) — rather than reconciling off an empty snapshot, which would reset overlay-backed fields + delete every category (PLAN-07/07.4 review; a same-schema *corrupt* manifest bails the same way — `read` throws `corruptManifestFile` on an unparseable file, a missing `name`/`slug`, or a list-shaped membership field that is not a sequence, staying tolerant only on additive scalars — PLAN-10), and that is idempotent (a no-change rebuild is all-zero). An overlay is authoritative **only when present**: for a skill whose row already exists but whose `manifest/skills/<slug>.yaml` is ABSENT, the reconcile **preserves** the row's overlay-backed fields (scope/tags/cursor/origin/createdAt) rather than resetting them to defaults — the manifest is silent, not authoritative-empty — updating only the on-disk-frontmatter name/description (PLAN-12 / 12.3; the data-loss root that the import-side overlay write, this preserve rule, and `LaunchReconciler.manifestHasContent` now guard in depth). **`StoreMigrationService`** is the one-time, idempotent, launch-time backfill that brings every existing owned skill up to the self-describing model (frontmatter + overlay) **without losing a description** that lived only in the file or `cursorConfig` (origin-aware name precedence, file-preserving description precedence, row backfill). **`ManifestService`** keeps the overlay current at the **enumerated maintenance sites** — a skill create / **import** / metadata-edit / delete, a category rule change, a project register / remove — each regenerates the affected manifest from SwiftData, so a rebuild reproduces the live store. Bulk **import** *was* the one deliberately-deferred site (the 07.3 scoping) — an imported skill's overlay was left for the next single mutation or the one-time launch migration to write — but **PLAN-12 / 12.3 retired that deferral**: the launch rebuild now treats the manifest as authoritative *and* the migration runs once-ever, so a deferred (overlay-less) imported skill would be reset to defaults on the next relaunch. Import therefore regenerates the overlay immediately after its save, exactly like every other synced-state mutation, so no rebuild or sync (PLAN-08) can ever consume a store with a missing overlay. **The regeneration is atomic:** `ManifestService.write` builds the whole manifest in a UUID-unique sibling tree *outside* the store (`~/.pensieve.manifest-build-<uuid>.tmp`, same volume, so sync's `git add -A` can never stage a partial build) and then swaps it in via `FileService.replaceItem` (`renamex_np` `RENAME_SWAP`, or an atomic move on first write), so a write that fails part-way leaves the previous `manifest/` byte-for-byte intact — the launch rebuild and the daemon never observe a half-written manifest (no schema-only tree that would delete categories, no partial overlay set). Because the temp tree is built fresh, there are no stale files to prune. Together, the import-side overlay write, rebuild preservation of an existing row when its overlay is absent, and atomic manifest writes close every deferred/partial-manifest data-loss path the 12.3 launch rebuild could otherwise hit. The load-bearing invariant across every write path: `name` and `description` are always non-empty (name required at create + slug hardened non-empty; description falls back to the name), so no skill is ever dropped on a fresh-machine rebuild. PLAN-08 adds `GitService` + the `SyncEngine` on top of this store; PLAN-09 the body-conflict UX.

**The sync layer (BETTER-1, PLAN-08) — three services beneath the store.** Sync is pure plumbing over the already-portable PLAN-07 store: `~/.pensieve` becomes a **git working tree**, and each machine rebuilds its SwiftData locally, so the database is **never** synced — it and every out-of-tree app file live under `~/Library/Application Support/Pensieve` (`Constants.pensieveAppSupportDir`), deliberately outside the synced `~/.pensieve` root. Three services (`Pensieve/Services/`): **`GitService`** is the app's **first subprocess** — a synchronous, throwing wrapper over `/usr/bin/git` (absolute path). It is the one **sanctioned exception** to the `FileService` chokepoint: git owns `.git` and its own writes, reached only here. Arguments are **always** an array passed directly to `posix_spawn`, never a shell string, so there is no command-injection surface; every op taking a user-supplied remote/path positional puts a `--` end-of-options terminator before it (git parses a leading-dash or `--upload-pack=<cmd>` positional as an *option* it would execute — a git-option-injection class distinct from shell injection). The child environment is built explicitly for a **Finder/Spotlight launch** (which inherits neither the login-shell PATH nor the ssh-agent socket): PATH augmented with the standard git/ssh locations, `GIT_TERMINAL_PROMPT=0` to fail fast instead of hanging on a TTY-less prompt, `SSH_AUTH_SOCK` passed through, and the Pensieve-owned `GIT_ASKPASS`/`PENSIEVE_GIT_*` vars stripped-then-set so a `.sshAgent`/`nil` op can never ride a stale parent askpass. **`CredentialStore`** (`KeychainCredentialStore`) is the Keychain boundary: an HTTPS PAT is stored in a **Pensieve-namespaced `kSecClassGenericPassword`** item whose service string is derived from the bundle identifier — `<bundle-id>.git.<host>`, i.e. `com.jaredatch.Pensieve.git.<host>` in Release and `com.jaredatch.Pensieve.debug.git.<host>` in a Debug build, so a store/delete can never touch a non-Pensieve credential and a Debug build can never read or replace a production one. The GitHub install credential uses the separate `<host>#install` slot, never the sync credential. The PAT reaches git only through the **child process environment** via a secret-free `GIT_ASKPASS` helper — never argv (invisible to `ps`), never `.git/config` or a cleartext file (the out-of-store helper is 0700, written through `FileService.writeExecutableFile`). The app and daemon receive the helper path from their runtime paths value, including sync and the GitHub-skill services. ssh remotes store no app-side secret (ssh-agent passthrough). The connect-a-remote onboarding (`SyncSetupModel.parseRemote`) is a strict **transport allowlist** — https / ssh / scp-style only; `ext::`/`fd::`/remote-helper syntax, a leading `-`, and https-userinfo (`user:tok@host`) are all rejected before any URL reaches `GitService`. **`SyncEngine`** ties the store to git: `snapshot → manifest write → install the `merge=union` `.gitattributes` for the LIST-shaped manifest files (category files + the now-constant `projects.yaml`, kept for older builds' entries) → commit → pull --rebase → rebuild → push`. Concurrent set-edits (a skill joins a category) auto-merge via git's built-in union driver + dedup-on-read; a genuine same-entity body/overlay conflict is **aborted (restoring the exact pre-pull tree) and surfaced structurally** as `.conflicted(paths)` — never silently clobbered, never a raw `<<<<<<<` marker — with the local commit left unpushed for a later resolvable sync. That `.conflicted` outcome + the `SyncStatusView` indicator are the exact seam **PLAN-09** consumes for the diff-and-pick resolution sheet. A `/security-review` over this surface (PLAN-08 / 08.5-a) found no exploitable path.

Store git commands override `core.excludesFile` and `core.attributesFile` with `/dev/null`, disable system attributes with `GIT_ATTR_NOSYSTEM=1`, and set `core.autocrlf=false` and `core.eol=lf`. Identity, credentials, URL rewrites such as `url.<base>.insteadOf`, and unrelated user/system configuration still apply. A store operation resolves its shared git metadata directory once, repairs local attributes, and applies these command rules through its runner. Pensieve owns the store's local `info/attributes`: it disables `text`, `eol`, `ident`, `filter` and `working-tree-encoding` conversions with precedence over nested skill attributes. Skill merge attributes are reset to unspecified; the root manifest list files retain `merge=union`.

Full store clone refuses an occupied destination before downloading, builds in a sibling directory, defers checkout until local attributes are installed, and atomically publishes after checkout succeeds. Publication accepts an absent or empty store directory and refuses a nonempty destination, including one occupied during preparation, with a descriptive error. The live store stays untouched during preparation. Caught failures remove the sibling best-effort only if it still exists. Launch cleanup sweeps abandoned `.pensieve-clone-<UUID>` siblings under the sync lock, preserving names outside that exact UUID namespace.

Existing stores receive the same local rules before worktree operations. Pensieve does **not** run a one-time renormalization or create a migration commit for blobs previously committed using CRLF conversion, ident expansion or filters such as LFS. Those committed blobs stay as they are. A later checkout materializes their stored bytes without conversions. A later ordinary sync may commit different on-disk bytes when git notices a changed file stat; installing the rules alone does not invalidate git's cached stats. These repairs touch git metadata, never skill files. Rebase abort runs even if attribute repair fails; a successful abort is followed by reporting the repair error.

Pensieve excludes new, untracked `.env` and `.env.*` files except `.env.example`, `.env.sample` and `.env.template`; folders named `node_modules`, `.env` or `.venv`; and `.DS_Store` at any depth in the store. The three templates sync like other skill files, including when a skill ignores them. A template inside an excluded folder stays local. Names match exactly, so `.env.local.example` is excluded. These stay on disk unchanged. The exclusion belongs to the shared staging enumeration, including path staging and the daemon's clean check; it does not change the store's root `.gitignore` or a skill's rules. Other files hidden by a skill's `.gitignore` still sync. A store whose only pending additions are these excluded files is clean for the daemon; changes to tracked files still count. A file an older build already committed stays tracked, its changes still sync, and it is never removed because of this rule. An older app keeps its existing staging behavior because no new ignore rule is synced to it.

During sync and the daemon's fast-forward, an incoming tracked path cannot replace an excluded untracked local file, even when a skill ignores it. App sync checks before snapshot preparation and writing; rebase and daemon fast-forward also check before updating the worktree. Git inventories compare path bytes without opening local secret content and report wholly untracked excluded folders without walking their contents. A partly tracked folder retains individual untracked files, so an incoming sibling can sync. Wholly untracked subfolders inside it remain single receipts; replacements beneath indexed files retain exact child paths. Index inventories are scoped to excluded folders. A collision pauses with the file or folder's path and instructions to move or rename it, preserves local bytes and leaves no merge or rebase in progress. The daemon records the same message as a preflight failure rather than reporting divergence. Moving the local file lets the next cycle proceed. Rebase confirms origin/main still equals the checked incoming commit, uses Git’s own reflog fork point, and pins its new base to that commit. It ignores pull.ff and pull.rebase, never merges, and fetches no later tree. Adopting a remote during sync setup replaces admitted scaffold entries, including a root `.DS_Store`, by design.

Conflict inspection, stale-pick checks and resolution carry exact bytes. An absent side means deletion; present empty data means an empty file. The sheet keeps its text diff for UTF-8 sides without NUL bytes, and explains when a side cannot be shown as text, including binary and UTF-16 files. Choosing either side writes its original bytes.

A worktree check includes files hidden by a skill's own ignore rules. Skill-generated `__pycache__/` or `.venv/` content therefore pauses the daemon at `.dirtyTree` until an app sync carries those files; the daemon cannot fast-forward over pending skill bytes. Git's untracked-file enumeration identifies new nested repositories, whether ignored by the skill or visible. These stay local, never become gitlinks, and do not make the daemon's worktree check dirty. A skill already tracked by the store keeps syncing its ordinary files when it gains a `.git` entry, including when `skills/` itself becomes a repository. Sync never removes indexed files just because a nested `.git` appears. A stray `.git` marker that git does not recognize as a repository does not exclude the surrounding files. Staging updates tracked paths before enumerating new ones, preserving directory-to-symlink replacements without a separate tree walk. Launch reconciliation's clone and vendor sweeps use the caller's held sync lock; independent cleanup calls acquire their own.

Staging first applies the store's root `.gitignore`, then force-stages additional skill files enumerated without global or per-folder ignores. Root excludes, including `.DS_Store`, and local `info/exclude` still apply. The additional paths pass through a temporary NUL-delimited literal pathspec file under git metadata, removed after staging. A skill's `.gitignore` and `.gitattributes` remain on disk and in the commit, preserving its installed content hash. GitHub shallow clones and upstream history operations retain their source repository's rules.

GitService launches git in its own session and process group, without a controlling terminal, with an empty signal mask and default dispositions. It reads both pipes on the calling thread with nonblocking descriptors and waits for pipe readiness or git exit through kernel events. A call returns git's exit status and the output queued when git exits, then closes its pipe ends. The holder guarantee describes Pensieve's actions: A detached process holding or writing a pipe neither delays the call nor receives a signal. A write after the call returns fails with EPIPE or SIGPIPE, as the kernel decides. A local read failure throws `GitError.outputReadFailed`, saying Pensieve couldn't read git's output. The runner kills git's process group before reaping git, so helpers in that group stop too and a recycled pid cannot receive the signal. After a reap attempt, including one that throws, Pensieve sends no further group signal. Reap failures remain local GitError failures. A read failure after git exits also returns without waiting for an inherited pipe. The usability probe throws the same local read error and supplies no host-usability evidence for it. Fault hooks compile only into the disposable test probe.

A git remote answer is absent only on a known absent result: a successful empty URL, no origin in a readable repository, or a no-follow `.git` lookup reporting absence followed by confirmation that the store root is still a directory. Other failures are unknown and stop sync before preparation or writes. A missing store folder remains unknown. AppRuntime keeps ordered git-usability results in memory, probes off the main actor, and shares the resulting configuration with Settings and sync status. Unusable git preserves active sync and conflict states and pauses scheduled cycles until a probe or successful git operation reports recovery. Configuration reads and git evidence have separate ordering. A read that skips git cannot replace usability evidence. Completed configuration answers share one clock across runtime refreshes. An older read never replaces a newer answer. A configuration-read failure with usable git permits scheduled cycles to retry the repository. Settings offers Connect only after a completed configuration read proves absence. A cycle result never changes that answer or retires an outstanding read. A cycle with an origin but no local branch returns `branchless`. The footer and detail banner say "Can't sync yet: the store has no branch" instead of a healthy sync time. Connect remains unavailable while the origin exists. Configuration reads also probe local branches. Ordinary scheduled, retry-driven, watcher, manual and launch-preflight requests can re-check a branchless store without writing it. The next tick, wake or Sync Now discovers a branch created outside the app. A failed configuration read clears stale branchlessness while git remains usable. The daemon records the same `skipped / branchless` outcome before its worktree check. Runtime configuration refreshes run off the main actor, including window appearance and conflict completion. Those window callbacks reuse known usability without probing. The older launch-ingestion remote check remains synchronous. The read after a cycle supplies its current URL, absence or error. Cycle failures retain their own message through the single-line formatter.

**The GitHub install and skill-update layer (BETTER-4 / BEST-1 provenance slice, PLAN-19).** `SkillInstallURL` parses the supported GitHub repository, directory, and `SKILL.md` browser links; `InstallRemotePolicy` is the stricter stored-coordinate admission boundary and reconstructs the only clone remote git receives. `SkillInstallService` shallow-fetches, performs the bounded repository discovery, vendors complete regular-file trees, handles collisions and rename, adopts existing skills without changing their bytes, previews a pinned update, and atomically re-vendors an applied update under `sync.lock`. It writes the schema-v3 `InstalledOrigin` through `ManifestService.upsertSkillOverlay` and refreshes the SwiftData cache. `UpdateCheckService` batches linked skills by repository/ref, resolves heads with credential-isolated `ls-remote`, shallow-clones moved heads once, compares per-skill git trees, pins the checked commit/date/tree locally, computes stable local drift on demand, and never writes the synced overlay during a check. Both services use only the `github.com#install` credential or anonymous access; they never fall back to the sync credential. `SkillInstallViewModel` drives paste → fetch → pick → vendor/adopt; `SkillProvenanceViewModel` derives links, dates, drift, and per-skill check state (the list's filter and sort belong to `SkillListQuery`, a pure function over the skills, a `SkillListSpec`, the deploy index, and the categories — PLAN-29); `UpdatesViewModel` derives the notice/list (surfacing each update's validated source repository and in-repo path), explicit drift confirmation, re-check, and batch apply. `ViewChangesViewModel` owns the auxiliary window's bounded folder preview and selected file independently of the sheet. The window's Update action brings the main window forward. A closed Updates sheet opens through `confirmLeavingAnyDraft` with only that skill selected. An open, loaded sheet adds the skill's row to its selection. An applying, loading or failed sheet only comes forward. Only the sheet applies updates and owns their progress and results, including local-edit confirmation. These view models keep filesystem, git, hashing, and other expensive service work off the main actor; their `@MainActor` completion paths perform the compact SwiftData fetches and merges that update presented state.

`SkillInstallService`, `UpdateCheckService` and `UpstreamHistoryService` require their git service, credential store and scratch root. Install also requires its store root and lock path; update checks require their store root and content hasher; history requires its content hasher. The caller supplies each dependency without a live-state initializer default. `AppRuntimePaths` builds their git services with `git-askpass.sh` under its Application Support directory and their scratch folders under that same directory. Launch cleanup uses the same scratch paths, store root and lock path; the four service cleanup functions require explicit paths. `stableContentHash` reads the supplied directory through its `FileService` and hashes relative paths, file bytes and executable flags. It does not use the store root or install lock. Temporary runtime paths share one in-memory credential store across their services, so authenticated operations stay within the supplied roots.

Update checks leave a source batch's skill state unchanged when git is unusable or the network fails during its head read or clone. A run reports one environment error while saving the sources that answered. Authentication and missing repositories remain per-skill errors. A run advances the automatic-check timestamp unless it has an environment failure and no head read answered. A local operation or save failure is reported and waits for the normal interval before another automatic run. The service owns result persistence. The main-context presentation merge does not save unrelated editing state. A failed service save is reported alongside any environment error. Empty and all-authentication runs count. An all-offline run stays due for the next launch. Any completed check with an environment failure and no answered source suppresses further activation retries in that session. Other outcomes leave the deferral clear. A new launch, a manual check starting, or recovery from known-unusable git clears it. A manual check that fails for the environment sets it again. Another usable answer while git is already usable does not retry an offline check. Local read and save failures do not defer checks. Manual checks remain available. Environment failures during a clone or tree read preserve the whole batch. Other clone failures affect only pending skills. One classifier carries actual usability evidence to the runtime, with at most one diagnostic probe per batch after the run preflight. Developer-tools text in command stderr is only a hint because a repository can control it. A diagnostic probe must confirm it before the error becomes a host failure. A later local failure preserves that evidence and still counts toward the interval. Positive update-check evidence refreshes the remote even with background sync off.

`RuntimePaths` resolves the process's store, Application Support directory, home and agent roots. It is shared with the daemon. `AppRuntimePaths` forwards that value's git, lock, skills and deployment construction. Path-bearing services, view models and views require their roots or dependencies; they have no live-location or Keychain defaults. A temporary paths value selects an in-memory credential store, inert agent detection and agent roots under its Application Support directory. Its inert link service reports the same `DeployPaths` layout that backfill and post-sync reconciliation use. Hermes retains its default category below the sandboxed agent root. Sync, settings and conflict resolution share that credential store with install, update checking and history. `DeployPaths` takes its canonical and agent roots explicitly. `RuntimePathGuardTests` exercises `script/check-live-defaults.py`, the lexical check also run by lint and before the suite. It reports file and line for direct live-path constants or Keychain construction outside the named resolver files. Constant definitions and process-level path selection are named exceptions. The guard and its tests share `script/runtime-path-members.json`, which classifies location and non-location members. It checks direct static declarations in top-level `PathConstants`, `Constants` and their unqualified extensions. An unclassified declaration fails with its member name, file and line, including inside otherwise exempt definition files; an unparsed declaration cannot be classified by its diagnostic placeholder. New members require classification during review. Nested types named Constants or PathConstants are local names when tokenized braces balance. Unbalanced braces fail closed: constants types are treated as global, and no local shadow exempts their references. The global constants metatypes cannot escape the resolvers. Outside process-level production callers, implicit `.production`, `RuntimePaths.production` / `AppRuntimePaths.production`, and recognized metatype receivers (`Self`, paths types' `.self`, `self` inside a paths type and `type(of:)`) fail except as direct `==` or `!=` operands (including grouping parentheses and `guard` conditions) or case patterns. A pattern ends at `in`, `=` or `:`. Call arguments, including generic initializer arguments, are not comparison operands. Other value receivers' properties named `production` are allowed. Comments and strings are recognized before operators, including when a comment immediately follows an operator.

This guard matches text, without compiler-enforced production tokens or data-flow analysis. Its classification scan does not cover module-qualified extensions, second bindings in a declaration or nested types inside the global constants types. The tokenizer does not understand Swift regex literals. Classification is by member name only, so a non-location name forwarding a location can pass. These are guard limits, not permission for collaborators to resolve live state.

**The resident runtime (BETTER-2, PLAN-23).** `AppRuntime` owns the explicit `ModelContainer`, long-lived platform/library/sync and update-preview models, file watcher, `SyncScheduler`, and the asynchronously bootstrapped `SyncCoordinator`. It belongs to the process, not a window. `PensieveApp` injects that one runtime into the main window, Settings, and `MenuBarExtra`; `PensieveAppDelegate` keeps the process alive after the last window closes and recreates the main window on reopen. `SMAppService.mainApp` provides the user-controlled Launch at Login setting. The scheduler queues a launch run, ticks every 900 seconds, listens for wake, and debounces synced-state mutations for 30 seconds. It permits one cycle at a time and coalesces overlap into one follow-up. Background cycles do not run before coordinator bootstrap and launch ingestion are both ready, while sync is conflicted, without a configured remote, or while another actor holds `sync.lock`. Sync Now is refused from every entry point while the store is conflicted, and a conflict resolution can't start while a cycle is in flight, so the two never overlap.

Git recovery queues one catch-up after the entire in-flight cycle callback, including its configuration read, regardless of the cycle outcome. With no cycle in flight it requests one immediately. A queued manual, scheduled or watcher request absorbs the catch-up. A new recovery during that catch-up earns one more; no new recovery earns none. Conflict, known absence and a branchless store refuse catch-up. The scheduler refuses conflict and known absence before considering host usability. Unusable or unobserved git holds privileged pending requests and drops scheduled-only triggers. Any accepted usable evidence lets held requests drain, including the first usable answer after a failed bootstrap probe. Direct Sync Now runs regardless of cached usability so its git operation or coordinator preflight can supply fresh evidence. Request standing passes through the scheduler and a busy model: queued Sync Now and required launch preflight retain their background-preference bypass and priority. Coalescing retains each request kind. Refusing a stale or ineligible recovery retry redispatches the ordinary requests it absorbed through their own preference, eligibility and priority rules. Retry validity is checked before a busy model queues it, and cycle completion cannot re-arm a spent retry. A scheduler-admitted cycle cancels the pending debounce only when it starts. A refused request that starts no cycle, and a direct Sync Now, leave the debounce intact. With background sync off, recovery retries the user's failed Sync Now once at manual priority when sync is then allowed. A recovery following only scheduled work starts no cycle. Usable evidence after the failed manual cycle disarms its retry unless that evidence recovers the outage following the failure. Later cycles or usable evidence can retire the retry before it runs. The retry spends that user request only when its cycle starts and cannot re-arm itself.

`SyncCoordinator` is an actor with an owned serial dispatch executor, so its synchronous engine and SwiftData work run outside the cooperative pool. Each cycle creates and uses a fresh `ModelContext` within one synchronous executor job. `SyncEngine` still owns the one `sync.lock` acquisition; its `prepare` hook runs after the pre-write guards and immediately before snapshotting. The coordinator uses that hook to rebuild stale SwiftData after an external fast-forward and then publish this machine's `machines/<id>.yaml` state, so the snapshot cannot revert a CLI pull. A successful cycle returns to the main actor for `PostSyncConvergence`: `DeployReconciler` self-heals after every success, and a HEAD-advancing cycle runs category and intent reconcilers in order on another fresh context. The app and CLI share bounded `daemon-status.json` and `daemon.log` audit artifacts through a dedicated leaf lock.

Cleanup or persistence failure retains registration, reports the error and permits retry. Saved intents can already be withdrawn before a file is removed; copy reports that separately from physical progress. The retained registration still belongs to its categories, so ordinary convergence can restore removed category artifacts until retry completes, even without an identity sibling. Same-key siblings can also keep direct requests live. If withdrawal save/publication fails, rollback, restoration and best-effort manifest repair preserve or report the saved intent state.

Removal affects only this Mac. Other Macs keep their category deploys. Registering the same identity again restores its category deploys at the next convergence without editing the rule. An identity key with no registered checkout stays in its categories and deploys nowhere. Registering any checkout with the same identity lets the user turn off its category membership. Category skills redeploy at the next convergence before that membership can be turned off.

A missing or uncheckable folder still gathers local candidates. The confirmation names its path and promises later cleanup only when candidates will become waiting entries. Missing folders without evidence and relative saved paths promise no later cleanup. Execution saves waiting removals before request withdrawal, deployment-state retirement or ledger deletion, then unregisters. If that save fails, all source rows and records remain. Project-candidate classification checks folder reachability immediately after an absent lookup. A folder that disappears after admission therefore fails cleanup instead of retiring its evidence. Failure retains registration and evidence, while previously saved requests remain withdrawn. A failed project-removal attempt withdraws its new waiting entries only if no deployment evidence was retired. After deployment-state or assignment retirement saves, waiting entries survive a later failure. They don't wait for a retry: once the folder is back, the next reconciliation settles them while the project is still registered, retiring any whose path a current request holds. Older source/path entries remain.

**Waiting removals.** `WaitingRemovalStore` persists schema-versioned cleanup intent in `waiting-removals.json` under Application Support, with its own leaf lock. Entries hold a UUID, source identity, project name/path and optional identity key, artifact path, agent, slug and optional legacy Cursor fingerprint. Creation deduplicates by source and path; completion retires only the snapshot's UUIDs, preserving newer entries at the same path. No backfill, rebuild or healer replaces this store. Refused reads pause cleanup and report a problem while keeping its bytes.

`WaitingRemovalReconciler` runs once after the category and intent phases at launch or sync with changes. Direct user reconciliation also runs it. `ProjectFolderProbe` shares each folder's bounded answer between admission and desired-state reads. With no reachable entry, the pass reads no desired state. Otherwise it reads all current requests before removing anything. Missing and uncheckable desired projects contribute unresolved paths; resolution failures inside reachable folders pause the pass. Deployment-state records count as requests for live skills in registered projects, including keyless direct deploys. Historical deployment rows alone cannot keep a path requested.

Cleanup uses the entry's path and Pensieve's artifact ownership rules, whichever checkout is there. The project identity key is kept for the record and is not compared. Current requests protect paths across all registrations by resolving the artifact's parent without following its occupant. A requested path retires its waiting entry without deletion.

Reachable unrequested paths execute through `DeployRemovalService`, with each ownership check immediately followed by its delete. An absent or inconclusive occupant needs a fresh folder check before its entry can retire. That check bypasses admission's cache and shares one new answer among entries in the same folder. Missing or uncheckable folders keep those entries quietly. Foreign occupants retire the entry. Marked Cursor rules use the ownership mark; unmarked legacy rules compare the retained SHA-256 digest and byte count. Without source evidence, legacy output is foreign.

Waiting removals do not enter the manifest, store repository, machine observations, deployment index or daemon listing. The daemon's explicit source list excludes the waiting store and reconciler, and the daemon never runs them.

**Content — rendered and source:** the Content tab's rendered view and editor read `SkillLibraryViewModel.readBody`, which runs `SkillParser.stripFrontmatter` over the raw file (see §4 — frontmatter on disk is real and canonical). A body save re-reads and parses the file, then writes through `SkillStore.rewriteSkill`, which splices the new body into the file's own bytes — frontmatter keys Pensieve does not own, fences, spacing, and the trailing-newline state stay exactly as written — and a metadata edit regenerates the manifest overlay; `Skill.updatedAt` is bumped manually (SwiftData does not auto-touch it). The rendered view installs Pensieve's own MarkdownUI image providers (`PreviewImageProvider`): no network request, only embedded images and images inside the skill folder, read through `PreviewImageLoader` under byte, type and pixel caps and a decode budget per rendered preview (`PreviewImageDecodeBudget`, PLAN-48). The editor's text is a draft on the view model (`drafts`, keyed by slug) until Save: `noteEditorChanged` opens an entry at the first differing keystroke and closes it on a return to the file's text, dirty is measured against the fingerprint (so a file that catches up reads clean without the entry going), `saveDraft` writes it through `updateBody` and re-seeds the fingerprint, `discardDraft` drops it, and `confirmLeaving` is the one gate every way out of an edited skill passes — the view model, not a view, decides what an external change does to a dirty editor (ask, never reload). The detail's snapshot (`DetailContentSnapshot`) also carries the skill directory's inventory (`SkillBundleInventory`, PLAN-34) and the deploy status of every installed platform for This Mac and each registered project, all read in the loader. The loader re-runs on the skill, an external change, an app write, a deploy change, a project change, and every watcher event — a change to a bundle file other than `SKILL.md` reaches the app only as an event the body check calls an echo; the Content tab's other-file text is re-read on the same signals. The detail is one header over tabs (`DetailTab`, `Views/SkillViews/Detail/`); the tab switch, the file pulldown, and the rendered toggle are ways out that pass `confirmLeaving`; Delete asks its confirmation alone. History is the tab's timeline over `GitService.log` (`SkillHistorySnapshot`, read when the tab is shown); Restore confirms and writes through `restoreSkillHistoryVersion`, which drops a draft only after the write; the sheet remains the conflict flow's.

**Rebuild / migrate (PLAN-07 + PLAN-12 launch catch-up):** on launch `LaunchReconciler.reconcileOnLaunch` first tries to rebuild SwiftData from the file store when the manifest is authoritative/readable enough to consume, before the watcher starts and before any manifest write. `StoreRebuildService.rebuild(fromRoot:context:)` reads the manifest once, admits only skills whose `SKILL.md` has required frontmatter (skip + warn otherwise), and converges SwiftData's `Skill`, `Category`, and `MachineDeployIntent` rows to disk + overlay (insert/update/delete, idempotent). It retries once if `.git/HEAD` advanced mid-rebuild, so a daemon fast-forward that lands during launch gets one bounded re-read. When the rebuild bails `storeUnreadable` (a newer schema or a corrupt file), the outcome fences every add through `SkillLibraryViewModel.addsFenced` — until a sync cycle gets past the engine's pre-write read (`.synced` or `.conflicted`) or a relaunch reads the manifest; edits stay open. Only after a clean rebuild does the one-time `StoreMigrationService.migrateIfNeeded` backfill not-yet-self-describing owned skills (frontmatter + overlay); that migration write is skipped when `sync.lock` is busy or HEAD moved since the rebuild, and the marker persists only on all-clear. Neither path invents a path-less `Project`: a synced project *identity* with no locally-registered `Project` simply doesn't fan out.

**Category assignment / reconcile (PLAN-06):** a toggle in `CategoryDetailView` (or a sidebar category CRUD action) calls `CategoryStore.setSkill`/`setProject`/`delete(...reconciler:)`, which mutates the rule arrays and then calls `CategoryReconciler.reconcile(context:)`. The reconciler resolves the stable keys to live `Skill`/`Project` objects (skipping any dangling id), computes desired-vs-current `(skill, project, platform)` triples, and drives `PlatformViewModel.deployBatch`/`removeOwnedBatch` (which classifies ownership first) per `(skill, project)` group — inserting a `SkillProjectAssignment` ledger row per *successful* deploy and deleting one per *successful* unlink. The returned `BatchResult` surfaces successes quietly and failures in the §5 (`BulkDeploySheet`) tone.

**Resident sync and convergence (PLAN-23):** the scheduler hands one trigger to `SyncCoordinator`, whose owned serial executor opens a fresh context and calls `SyncEngine.sync(...prepare:)` within one synchronous job. Under the engine-owned `sync.lock`, `prepare` rebuilds if the last ingested HEAD is stale or unknown, then publishes this machine's state file. The engine snapshots, commits, pulls/rebases, rebuilds, and pushes. On success, `PostSyncConvergence` runs deploy self-healing; when the cycle ingested a new HEAD it also runs category and intent reconciliation in order on a new main-actor context. A conflict runs none of those effects and remains in the existing resolution flow.

**Machine deploy intent (PLAN-23/36):** in user-wide mode, `BulkDeploySheet` gives each skill/agent choice a machine multi-select. In project mode it writes project-scoped intent for This Mac. `DeployIntentModel` replaces the selected rows in SwiftData, writes schema-v5 per-entry files, saves, nudges sync once, and invokes the local intent reconciler. A This Mac selection can realize immediately. An apply that changes the selection's rows then runs the local intent reconciler, so an apply that drops This Mac retracts its intent and removes the deploy that intent owned. An apply that changes no rows skips that reconcile unless This Mac is selected. A remote-only selection adds no local deploy of its own. The Deployments tab's remote switches take a persistence-only path instead: they write the addressed intent, nudge sync, and run no local reconcile. Retraction deletes the per-entry fact. One file can also carry project-scoped entries, addressed by the project's cross-machine identity key and a platform list. `IntentReconciler` considers this machine's user-wide and project rows for locally installed platforms, resolves slugs and registered project identities to local rows, and diffs desired pairs or triples against `IntentAssignment`. It sends all file effects through `PlatformViewModel`; failed removals stay ledgered for retry, another owner's deploy survives, and unledgered manual deploys survive until a matching intent adopts them.

**Machine observation (PLAN-23/36):** `MachineIdentity` reads or creates the canonical UUID in app support. During `prepare`, `MachineStateService` composes detected agents, stable project identities with optional display-only home-abbreviated paths, and realized `deploy-state.json` records, then atomically replaces only `machines/<own-id>.yaml` when its content changed. `ContentView` tolerantly reads those state files after launch and sync-state changes. The Machines `SidebarSection`, its `MachineListView` content, and each `EntitySelection` detail are read-only; remote-only projects never become local `Project` rows.

**Where state lives:** `AppRuntime.makeContainer` defines the SwiftData schema for skill/project metadata, historical deploy records, categories, `MachineDeployIntent`, and the local category and intent assignment ledgers. Settings are `@AppStorage` / `UserDefaults`, including the machine display name and background-sync preference. The canonical body, schema-v5 manifest overlay, `machines/` state, and deploy artifacts are on the filesystem. `machine-id`, SwiftData, audit files, `deploy-state.json` and `waiting-removals.json` stay under app support; sync credentials live in the macOS Keychain (`KeychainCredentialStore`) and settings in `UserDefaults` — all machine-private, none of it synced.

## 4. Cross-cutting concerns

**Error handling.** Error typing is **uneven** today: the git, sync, install, and update services define typed `LocalizedError` enums (`LinkError`, `GitError`, `SyncError`, `CredentialError`, `SkillInstallError`, `SkillUpdateFlowError`, `UpdateCheckError`, `MachineStateError`, `SkillInstallURLParseError`); `SkillStore` throws a plain `SkillStoreError: Error`; `FileService` throws `ProjectFolderError` and `SymlinkCreationError` for their defined cases and otherwise propagates Foundation/`NSError`. View models `catch` whatever propagates and surface a `String?` `error` for the UI. Parsers degrade rather than throw. `SkillParser.parse` returns an all-body `ParsedSkill` when the YAML frontmatter is absent or unparseable. PLAN-07 read it through Yams. PLAN-38 now checks it before construction. Admission is gated separately by `hasRequiredFrontmatter`, not by "did it parse." No silent empty-catches in services — a manifest-regeneration or store-save failure is surfaced (a warning or the view model's `error`), never swallowed by an empty `try?` (the recurring PLAN-07 review rule). (Standardizing on typed service errors is a reasonable future convention — not yet reality.)

**Frontmatter on disk is now intentional and canonical (PLAN-07).** Before PLAN-07 the store was *intended* to be clean body-only markdown and any frontmatter was merely hidden at read time. That is **reversed**: an owned `SKILL.md` **is** a self-describing file — YAML `name`+`description` frontmatter + body. Pensieve composes that canonical file only when it creates one: `SkillStore.createSkill` for authored skills and Cursor rules, and local import when a source's frontmatter can't be preserved, which puts the whole source under a fresh two-key header (`ImportViewModel`, PLAN-42). Frontmatter opens only on a file's first line and closes at the next column-0 `---`, as agent readers do; a block holding `---` anywhere never has its entries rewritten. Entries are trusted for a splice only where YAML's key positions match the scanner's, and `SkillSerializer.normalizeIdentity` re-parses its own output, for import and migration alike (PLAN-48). A local import whose frontmatter can be preserved is written with only `name` and `description` spliced; an edit-save goes through `SkillStore.rewriteSkill` and replaces only the body, and the store migration normalizes `name` and `description` by splicing just those two entries, leaving a file it cannot split safely unchanged with a warning (PLAN-37 — the old save re-emitted exactly two keys and dropped the rest, `license:` included). The editor still hides frontmatter at *read* time (`readBody` → `SkillParser.stripFrontmatter`) and the self-write fingerprint is computed on the *stripped* body, so the editor UX is unchanged while the on-disk file gains frontmatter. The **tolerant vs. required** distinction is load-bearing: `SkillParser.parse` tolerantly reads whatever frontmatter is present (missing keys → nil), but a separate `ParsedSkill.hasRequiredFrontmatter` (both `name` and `description` present + non-empty) is the gate at import preservation, migration, and rebuild admission — a body-only file *parses* (as all-body) but is **not** an admissible skill.

**Hashing / freshness.** Cursor freshness (`CursorCompiler.isUpToDate`) compares the full regenerated `.mdc` against the file on disk. `DeployRecord.contentHash` and `FileService.contentsHash` still use Swift's process-seeded `Hasher` and must not be treated as cross-launch or cross-machine signals. GitHub-installed skills use a separate stable SHA-256 tree hash from `SkillInstallService`: entry-counted fixed-width path/content digests plus owner-executable mode, in byte-sorted path order. `InstalledOrigin.contentHash` records that value for local-drift checks; `installedTree` remains the git-native upstream-change signal.

**Concurrency.** Leaf services remain synchronous and throwing. Resident orchestration is the narrow async layer: `AppRuntime` and `SyncScheduler` are main-actor-owned. Cooperative-pool callers of synchronous work that may run git use `BlockingWork.task` or `await BlockingWork.run`. The owned task executor starts a native thread per runnable job, so independent calls progress beyond the core count without occupying cooperative pool threads. It preserves the worker task's cancellation identity, and the await joins work and cleanup before returning. `SyncScheduler` starts startup, tick, wake and debounced nudge cycles at default priority. Required launch preflight bypasses the background-sync preference at default priority, using its own request standing. A queued Sync Now uses user-initiated priority, including when it absorbs background triggers; a direct Sync Now retains its caller's priority. `SyncCoordinator` uses a separate serial dispatch executor that maps each job's priority to dispatch-block QoS. Each synchronous cycle creates, uses and drops its fresh SwiftData context within one job on that executor. Add Project identity previews also run disk probes through `BlockingWork`. Editing the path cancels the previous preview task and shows neutral checking text for the current path. A 150 ms debounce starts disk work only after typing pauses; generation checks prevent stale results from publishing. An unchanged path starts no preview. Add is disabled while the current probe is pending; Return queues one submission after admission, and editing either field cancels it. Paths beginning with `~/` expand before preview and registration; input that remains relative is refused with a reason asking for `/` or `~/`. On submission, the identity service admits the directory before reading identity, and its marker write uses the bounded project writer. A completed probe permits retrying the same path after a failed Add. Tests inject the debounce scheduler. Preview and registration use the same bounded `FileService` folder check. Preview image loading is the leaf exception: loads run off the main actor through the document's budget queue, and its leaf reads stay synchronous and throwing. Each coordinator cycle and each ledger convergence pass uses a fresh context. Swift 5.10 strict concurrency remains off; do not invent other async seams below this orchestration boundary (see `docs/CONVENTIONS.md` §7).

**Security posture.** The app is **unsandboxed by design** (`ENABLE_APP_SANDBOX: NO`) — it needs to write symlinks across `~/.claude`, `~/.grok`, `~/.codex`, `~/.openclaw`, `~/.hermes`, `~/.cursor`, and arbitrary project dirs the user registers. Public releases are signed and notarized through PLAN-18; signing and publishing remain human-gated. The app reads and writes files in the user's real agent directories, so a path-construction bug has real blast radius — this is why `Constants` centralizes paths, `FileService` is the single chokepoint, and `LinkService.validatePathComponent` rejects an escaping `Skill.directoryName` or category (`.`/`..`/`/`/leading-`~`) before any symlink is created or removed (PLAN-04). A PLAN-04 `/security-review` over the new path/symlink surface found no exploitable traversal. PLAN-06's category reconciler deploys/removes across *many* `(skill × project × agent)` tuples in a loop, but every write still routes through `PlatformViewModel.deployBatch`/`removeBatch` → `LinkService`/`CursorCompiler`: the reconciler builds **no** path and does **no** file I/O (it passes `Skill`/`Project` objects), category rule strings (`projectKeys`/`skillSlugs`/name) are only lookup keys never path components, dangling ids are skipped, and the destructive reconcile removes only link *entries* within chosen project dirs (`removeItem(atPath:)` does not follow symlinks). A PLAN-06 `/security-review` over the fan-out write surface found no exploitable traversal (06.6-a). PLAN-07 adds one new untrusted-input surface — parsing **third-party YAML frontmatter** — handled by **Yams** (the same LibYAML-backed parser SwiftLint trusts for arbitrary `.swiftlint.yml`); parsed frontmatter values are read as data (`name`/`description`) and **never** used to construct a filesystem path or a shell argument. The manifest's one free-string→filename surface (category names) is encoded only through the safe `ManifestService.categoryFileName` (`slugify` strips `/`, `.`, and every non-`[a-z0-9-]` char, then a SHA-256 suffix), so a crafted category name cannot escape `manifest/categories/` (the §A filename tests are the executable teeth). A PLAN-07 `/security-review` over the Yams + manifest-filename surface found no exploitable path (07.6-e). PLAN-38 later replaced direct Yams reads with `CheckedYAMLLoader`, which validates LibYAML events before Yams constructs values. **PLAN-08 adds three untrusted-input surfaces — the git subprocess, HTTPS-PAT credential handling, and content pulled from a remote — all reviewed clean at 08.5-a** (see §2 "The sync layer"): the subprocess passes args as an array with `--` option terminators (no shell, no git-option injection), `parseRemote` rejects `ext::`/`fd::` remote-helper syntax that git would *execute* plus https-userinfo, the PAT never reaches argv/`.git/config`/disk and the Keychain query is namespaced so a delete can't wipe a foreign credential, and `StoreRebuildService` performs **no filesystem write derived from remote-controlled names** (it reads `skills/<slug>/SKILL.md` and writes only to SwiftData; the only manifest writes go through the sha256-safe `categoryFileName`). The structural teeth (args-as-array grep, no-`/bin/sh` grep, no-token-`writeFile` grep) are the executable checks in the 08.5-a Verify block. **PLAN-10 (BETTER-2 prelude) hardened all of the above — the deferred PLAN-08/09 review residuals — and passed `/security-review` clean over the whole branch (10.7):** the remote-admission policy moved into a single `RemoteURLPolicy` shared by connect (`SyncSetupModel.parseRemote`) and a new **sync-time re-validation** (`SyncEngine` re-checks the stored `.git/config` `origin` through the same policy before *every* network op — closing the "stored origin weaker than connect" gap), extended to reject interior newlines and to parse bracketed IPv6 hosts; `GitService.childEnvironment` now **strips the full inherited git-behavior-override family** (`GIT_SSH*`/`GIT_PROXY_COMMAND`/`GIT_EXTERNAL_DIFF`/`GIT_CONFIG*` + indexed keys/`GIT_ALTERNATE_OBJECT_DIRECTORIES`/`GIT_NAMESPACE`/`GIT_TRACE*`) while deliberately preserving the hardening `GIT_CONFIG_NOSYSTEM`, and the HTTPS token rides only the child env (never argv, the on-disk askpass-helper body, or `.git/config`; a helper-write failure now *propagates* instead of proceeding unauthenticated); `conflictedFiles` enumerates with `-z` (NUL-delimited), so an embedded-newline conflicted path is one exact entry instead of two fragments; the **manifest reader strict-shape-validates the list-shaped membership fields** (`project_keys`/`skill_slugs`/`tags`/`agents`) — present-but-not-a-sequence throws `corruptManifestFile`, fail-safe end-to-end (read throws → `StoreRebuildService.rebuild` bails mutating nothing → `SyncEngine.sync`'s pre-write read guard aborts before emptying or pushing) while additive scalars stay tolerant for forward-compat; and a **total canonical-store slug-dir guard** now holds — *Pensieve never reads, writes, or deploys through a symlinked `skills/<slug>` dir*, enforced at every sink (`SkillStore.readBody`/`createSkill`/`rewriteSkill`/`writeBody` via `validatedSkillDirectory`, `PlatformViewModel.deployOne`, `StoreMigrationService`, `StoreRebuildService` skip-with-warning preserving the row, `Skill.estimatedTokens`→0, and `SyncEngine.validatedWorktreePath`'s rejection of a symlinked non-leaf component; a symlinked *leaf* stays safe because atomic write replaces the link). PLAN-10's `/security-review` over this combined remote-URL / credential / symlink / manifest surface found no exploitable path (10.7). **PLAN-11 (BETTER-2) then consolidated that slug-dir guard into one primitive:** the five formerly-open-coded checks above — the three `SkillStore` body sinks (via the throwing `validatedSkillDirectory` wrapper), `PlatformViewModel.deployOne`, `Skill.estimatedTokens`, `StoreRebuildService`, and `StoreMigrationService` — now all route through a single reviewed **pure resolver `SkillStore.safeSkillDirectory(slug:base:fileService:) -> String?`** (returns `<base>/<slug>`, or `nil` for an empty/`/`/`.`/`..` slug or a symlinked/realpath-escaping dir). It carries the strongest form — component validation + symlink rejection + realpath-containment — *uniformly*, so the four sinks that previously open-coded a weaker `isSymlink`-only check are **leveled up** to it (they now also reject `..`/`/`/`.`/empty), and a sixth sink cannot bypass the invariant without visibly *not* calling the shared function. Each caller keeps its own control flow around the `nil` (deploy throws, token count returns 0, rebuild/migrate skip-and-preserve the row + warn — never throw, so the PLAN-08 row-wipe fail-safe is intact) — a **pure resolver, not a bare `throws`**, exactly so the fail-safe skip sinks need not catch. `SyncEngine.validatedWorktreePath` remains **separate** — it validates arbitrary multi-component git-relative paths with leaf-vs-non-leaf symlink semantics (a superset problem), not a single canonical slug, and is deliberately not folded in. This is defense-in-depth + anti-drift, not a bug fix (PLAN-10 confirmed all five sinks were already guarded); PLAN-11's `/security-review` over the consolidated guard found no exploitable path (11.3), and PLAN-12's daemon inherited `safeSkillDirectory` as the single call for any canonical slug path it touches.

PLAN-23 adds the synced deploy-intent control channel. Exact-canonical machine IDs and restricted slug/platform components are admitted before path construction; the parser refuses a wrong shape, a key mismatch or a bad component as a corrupt file, and the writer accepts only admitted components; `IntentReconciler` resolves only local skill rows and routes effects through the existing deploy sinks; per-entry files keep retraction out of union-merge semantics; and no new network operation bypasses `RemoteURLPolicy`. The PLAN-23 security review found no qualifying vulnerability across those bounds. PLAN-36 extends that accepted authority from agent home directories to the projects this Mac has registered: `IntentReconciler` also resolves project entries, but only to registered local projects, so someone with write access to the sync repository can cause Pensieve's own skill links to appear inside those projects, never in any other folder. Project keys are always written double-quoted. PLAN-38 makes `CheckedYAMLLoader` the one way Pensieve reads YAML, including the serializer's bare-scalar quoting oracle. It validates libyaml events before Yams composition or construction. It refuses a non-scalar mapping key, an explicit merge tag on a mapping key, nesting deeper than 64 total constructed levels including depth reached through aliases, merge nesting deeper than four levels including mappings reached through aliases or as merge-sequence items, and any node tag longer than 256 UTF-8 bytes either before or after repairing malformed UTF-8, whether written directly or expanded from a `%TAG` directive. The validator considers implicit merge spelling for every implicit scalar. A constant-time byte comparison matches Yams' merge regex: exactly `<<`, optionally followed by one final LF, VT, FF, CR, CRLF, NEL, LS or PS. Untagged scalars must still be plain, while an empty reported tag remains implicit in any scalar style. The same resolver instance is passed to every Yams construction call. It is module-internal, the narrowest visibility that lets the `@testable` target compare the byte classifier with the resolver actually in use. The suite audits this boundary in ordinary code with `CheckedYAMLLoaderTests.testAppYAMLReadsUseCheckedLoader`, which applies PLAN-38 criterion 38.2-e's load, compose, decoder, constructor and node-value patterns, widened to unqualified stream calls, whitespace and line breaks within calls, Yams `Parser` type references and `CYaml` references, to Swift sources under `Pensieve/` except `Pensieve/Services/CheckedYAMLLoader.swift`. Yams import detection covers attributes, declaration kinds, indentation and line breaks; CYaml token matching also catches imports with intervening comments. This is a textual audit, not a defense against deliberately hidden calls: `import /* x */ Yams` is not recognized as a Yams import. Alias expansion has a 100,000-unit cost budget. Each alias is charged once for its expanded subtree: one unit per repeated node, each scalar's UTF-8 bytes, and the full resolved-tag bytes. Implicit and non-specific scalars conservatively cost the longest tag Yams can resolve, a constant 27 bytes. An empty reported tag is normalized to implicit and receives that same charge. Explicit tags cost their decoded bytes. Implicit containers cost their resolved `seq` or `map` tag bytes. Alias-free literal data consumes no alias budget, but remains subject to the tag and merge-nesting caps. Its checked integer constructor makes an overflowing sexagesimal integer load as its string. Each reader maps a refusal to its existing parse-failure behavior, so manifest and sync reads fail closed, machine state is skipped with its warning, and skill frontmatter becomes the existing all-body fallback. For writing, the loader reports a bare scalar's constructed value and whether construction used the integer-overflow string fallback. The writer quotes a scalar that does not construct as the identical string. It also quotes the overflowing sexagesimal integer whose checked construction falls back to a string, because an older build's plain Yams constructor would trap. Other resolved tags that already construct as strings retain their legacy bare bytes. The writer escapes U+FFFE and U+FFFF because libyaml refuses either raw even inside a double-quoted scalar.

## 5. Extension points

- **New agent/platform** → add a `PlatformTarget` case, its `Constants` paths, and (if it reads standard `SKILL.md`) route it through `LinkService`'s symlink branch; `AgentDetectionService` gates whether the UI shows it. A non-standard format gets its own compiler alongside `CursorCompiler`. (PLAN-04 added OpenClaw + Hermes this way, and PLAN-22 added Grok; a generic custom-agent adapter is deferred — see PLAN-04 non-goals.)
- **New import source** → legacy/local scanners add a `scanX()` to `ImportScanner` returning `DiscoveredSkill`s. A network or registry source should normalize into `SkillCandidate`/`SkillFetchResult` and feed `SkillInstallService`, preserving the same vendor/provenance/update boundary. GitHub is the only shipped remote source; registry browsing, archives, `.cursorrules`, and `AGENTS.md` remain future.
- **Per-category agent selection** → an additive refinement of PLAN-06's category fan-out: because the `SkillProjectAssignment` ledger is already per-agent, a category-level platform preference can narrow the *desired* set without changing the realized row shape (promote `skillSlugs` to a join carrying `[PlatformTarget]`). Today a category assignment fans out to *all* project-capable installed agents.
- **Cross-machine control** extends the shipped resident convergence layer. Deploy intent is machine-scoped and can address the whole Mac or a stable `Project.identityKey`; `IntentReconciler` maps project entries to every matching registered local project and records each realized artifact in its project-aware ledger. Category fan-out remains a separate owner that composes with project intent. Any extension must preserve per-entry retraction, exact-canonical machine admission, locally resolved paths, and the existing deploy sinks.
- **MCP server / CLI (BEST-3)** sit beside the view layer: another caller of the same services. Keep business logic in services, not view models, so a non-GUI front end can reuse it.

## 6. Conflict resolution (PLAN-09)

When `SyncEngine.sync` hits a body/overlay conflict it aborts the rebase and returns `.conflicted([paths])` — a **safe resting state**: our commit is unpushed, `origin/main` is still divergent, the working tree is clean, no rebase is in progress (PLAN-08's interim). PLAN-09 resolves that seam with a **reproduce-conflict**-on-demand model: the conflict is never persisted mid-rebase; it is re-derived on demand through a shared prelude (`prepareLocalHead` — write the manifest snapshot + install union attributes + a **single-commit collapse** of unpushed divergence, so `pull --rebase` always replays exactly one commit) followed by `pullRebase`.

- **`SyncEngine.inspectConflicts`** reproduces the conflict, reads both sides, and aborts back to the safe resting state — returning a `ConflictSet` of correctly-labeled items (or `.cleared` if the conflict resolved itself upstream).
- **`SyncEngine.resolveConflicts`** reproduces the conflict, verifies it is unchanged (the reproduced blobs still equal what the user saw — else `SyncError.conflictsChanged`, and the UI re-inspects), writes the picked side through the path-guarded `validatedWorktreePath` sink, `rebase --continue`s (with a proven-empty `--skip` for an emptied "keep other"), rebuilds, and pushes. Any failure aborts the rebase back to the safe resting state.
- **⚠️ The rebase stage mapping — opposite of a plain merge.** During `git pull --rebase origin main`, **`stage 2` = `origin/main` = the OTHER machine**, and **`stage 3` = the replayed local commit = THIS machine**. `inspectConflicts`/`resolveConflicts` read `:2:`/`:3:` accordingly; inverting this labels every diff side backwards.

The diff and version-history views render this pulled/replayed content **inert** (CONVENTIONS §14). The reproduce-conflict engine, the value types (`ConflictSet`/`ConflictItem`/`ResolutionPick`/`ConflictInspection`), and the `GitService` conflict/history primitives are reusable by BETTER-2's headless/daemon path.
