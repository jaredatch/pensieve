# TESTING.md — Pensieve test strategy

How work is verified. The stronger and faster these checks, the longer an agent can run unattended. Stack commands live in the `macos-swift` module and the `script/` wrappers (PLAN-01); this file is the *strategy*.

## 1. The test hierarchy

The suite uses **XCTest**. Tests come in these flavors:

- **Unit (pure logic, no I/O)** — the default and majority: parsers and serializers (`ParserTests/`), pure view-model queries and row builders (`SkillListQuery`, `ListRows`), reconciler and policy logic against stubs.
- **Filesystem-integration** — exercise the real filesystem through a temp directory (`LinkServiceTests`, `CursorCompilerTests`, the store/manifest/rebuild tests). These create a unique temp dir in `setUpWithError` and remove it in `tearDownWithError`. **Never touch a real user directory in a test.**
- **Git-integration** — `GitServiceTests`, the sync-engine and install/update tests run real `/usr/bin/git` against bare repositories created in a temp dir and reached over `file://`. No test opens a network connection.
- **Behavior-via-log** — `AppSignalTests` asserts the `os_log` signal emitter through an injected sink (CONVENTIONS §5). New observable-behavior acceptance criteria should grow a signal + a test.
- **View-adjacent logic** (`ViewTests/`) — the sidebar selection bridge (`SidebarOutlineControllerTests`), diff and history presentation, import results. There are **no snapshot tests**; add them with an explicit precision policy if/when the view layer earns it. Hosted tests (`InstalledSkillHistoryHostTests`, the `SkillDetail*` layout tests) mount the production view in an `NSHostingView`, and the History ones press buttons they find through the accessibility tree. That tree doesn't reach every control: the menu-bar menu's plain SwiftUI Buttons (`PensieveMenuBarView`) expose no accessibility node in the test host, only its AppKit-backed Toggle does. Test such a control's decision on the model property it reads, and leave its rendered state to a manual gate (PLAN-41 / 41.2-c17). Hosted SwiftUI bitmap and PDF captures also return blank pixels in the test host, even for a plain red view. Test the model or image provider and leave on-screen display to a manual gate. Offscreen `ImageRenderer` checks must assert visible pixels before comparing captures; two blank images can compare equal.

For offscreen preview comparisons, rendered text allows at most 4 per RGBA byte; decoded images stay exact, and both require equal dimensions and visible pixels.

`ImportWizardHostTests` reads visible text and selection counts from the production wizard's live `NSHostingView._viewDebugData()` tree, including the nested hosts that render list cells. The wrapper forwards `SWIFTUI_VIEW_DEBUG=1` before each host launches. This inspection uses SwiftUI's underscored debug API and reflected SDK fields; missing data fails the UI assertions. It never evaluates a fresh view body or substitutes model state for rendered values. Return key actions drive refusal and retry in a hidden window, without OCR or window activation.

Not present: **network-integration** tests. When one is needed, tag it (§4).

## 2. Acceptance ↔ tests

Phrase checks as observable behavior and exercise it through the production path: the built binary, the launched app, or the real service boundary. Assert on a build result, a test result, or an `os_log` signal, rather than the presence of code. Signals use subsystem `com.jaredatch.pensieve` and dot-named events such as `app.launched`. Fixtures and stubs can add edge cases, but cannot be the only proof that production works. Confirm a check fails when its behavior is removed.

## 3. Mocks / fixtures

- Services are tested against their **protocols**; tests inject the real `FileService` over a temp dir (the default style) or a purpose-built double. There is no single shared mock layer: `FileServiceProtocol` doubles are written per test file for the one failure they need (`ThrowingWriteFileService`, `LockAssertingFileService`, `LeafRejectingFileService`, …), and the reusable ones live in `*TestDoubles.swift` / `*TestSupport.swift` files beside the tests that share them (`LinkServiceTestDoubles`, `SkillInstallTestDoubles`, `PostSyncConvergenceTestSupport`, `Fixtures/DeletionTestSupport`). Reuse an existing double before writing another.
- A view model that reconciles concurrent async work for one key is tested with a **sequence harness**. `UpstreamHistorySequenceHarness` holds every await point (disk load, read, probe, local measurement, persist) and releases them in a chosen order, and a generated test runs every reachable order with its counts pinned. Its waits are bounded by wall-clock time (`TestWait`), never by yield counts. Reuse it before writing another; PLAN-39 spent eight review rounds on races that one ordered sweep would have found.
- Each fixture store needs its own parent folder. Use `TestStoreDirectory`, keep sibling clones and locks under its `root`, and remove that parent at teardown. This keeps clone cleanup from reaching another fixture.
- File fixtures live in `PensieveTests/Fixtures/` (`sample-skill-*.md`, `sample-claude-skill.md`, `sample-cursorrule.mdc`). Keep new fixtures there.
- A test that hosts a view in an `NSWindow` sets `animationBehavior = .none`, closes the window and releases its owners in the test body or a teardown block. XCTest runs these blocks before `tearDown()`, so releasing a window in that override is too late. The bundle's `TestWindowLifetime` observer allows two seconds for cleanup, then rejects visible windows and closed windows that keep content or transitions. A hidden, contentless shell with transitions off passes. The guard excludes windows that predate the case and classes defined under `/System/Library/PrivateFrameworks`, whose helpers macOS retains. Public AppKit and SwiftUI classes, and app and test classes, still count. Transitions can retain a closed window and occupy a dispatch worker.
- Whether the test host becomes the active app varies by run, so `NSApp.keyWindow` may be nil or a window another test made key. A test that depends on which window holds a sheet leaves one candidate window on screen (PLAN-54 / 54.8). Dismiss a live sheet through its own state and wait for `attachedSheet == nil` before removing the view that presents it: tearing that view down under a live sheet crashes the host.
- `TEST_RUNNER_PENSIEVE_TEST_WINDOW_SAMPLE_DIR` enables native thread samples after each host finishes. When checking a full suite, verify sampling succeeded and compare each host's AppKit animation workers with a fresh `RuntimePathGuardTests` host baseline. That class hosts no window. For each sampled run, `test.sh` sleeps the display after acquiring the machine's test lock and wakes it when the run ends, including on failure or interruption. Callers leave display control to `test.sh`. With the display awake, animations finish and the worker comparison cannot detect a leak.
- `GitBlockingFixture` waits for its release file for at most its lifetime (90 seconds by default). Removing its fixture directory or reaching the deadline makes fake git exit 124, even if the test host never runs cleanup.
- Create test temp paths through `TestTemporaryDirectory.path` or `.url` (enforced by `lint.sh`). `test.sh` supplies a fresh root under TestRuns, deletes it on completion, and prunes interrupted runs. The test host bounds Git discovery at that root. This keeps fixtures and sibling lock files out of the shared macOS temp folder. Foundation ignores `TMPDIR`; Xcode runs use the system temp folder. Tests that need the real macOS alias or a short socket path use `.systemPath`, with a comment explaining why and cleanup for everything they create.
- A **novel test-safety mechanism** (a sandboxing double, a containment guard) ships with a **written contract** in its doc comment: the protocol surface it intercepts, the failure mode it enforces, and its deliberate exclusions. Reviewers judge against the stated contract instead of re-deriving the guarantee each pass — PLAN-22's `LinkServiceCanonicalDirectoryFileService` took a three-round hardening chain to converge, and the written contract is what ended it.
- A fixture that **stubs a production helper** (a shell function, a tool such as `hdiutil`) leaves that helper untested. Pair the stub with one test that runs the real helper against the real tool, and make the stub fail where the tool fails. PLAN-46's DMG mount check passed every release test behind a `test -d` stub and never matched a real mount, since macOS lists the resolved `/private/var/…` path (round 4). Then a detach stub that succeeded on a never-mounted path hid a defect in the cleanup trap (round 5).
- When production gains a **defaulted path parameter** (a constructor default resolving to live user state), audit **every pre-existing construction** of that type in the test target and inject explicit temp/neutral paths. A new default can silently repoint old tests at a developer's real data — PLAN-22 22.5's `ImportScanner.grokSkillsDir` default would have sent three pre-existing tests scanning the real `~/.grok/skills` without their hermeticity edits.

## 4. Test selection & tagging

- `script/test.sh` runs the full suite over `xcodebuild test`; `script/test.sh --filter Foo` runs a subset, where `Foo` is an XCTest identifier. A name with no `/` is prefixed with the `PensieveTests/` target, so `ClassName` works. A name with a `/` is passed as written, so a single test is `PensieveTests/ClassName/testMethod`: `ClassName/testMethod` names a target that doesn't exist and matches nothing (PLAN-36 / 36.1's first blocks). The wrapper refuses a filter that matches zero tests with a non-zero exit, so a misspelled filter cannot pass vacuously. Every run prints `PENSIEVE_TEST_COUNT=<n>`. Every run first takes the machine's test lock (an exclusive `flock` it waits for asleep), so a second run from any checkout waits in line instead of starving the first. The suite runs in parallel, one test class per worker. A parallel run prints no `Executed N tests` line, so the wrapper reads the count from the run's result bundle (`xcresulttool`). A passing run whose count it can't read fails. A failed run keeps its result bundle under `DerivedData/FailedRuns/` (the newest five) and prints each failed test with its message, so a failure that doesn't reproduce can still be read afterwards with `xcresulttool` (#61).
- Full and filtered runs launch hosts with `LIBDISPATCH_COOPERATIVE_POOL_STRICT=1` and Xcode's default test host count. The wrapper sets the forwarded variable before launch, even if the caller supplied zero. The git-entry, gate and history scheduling guards therefore run with one cooperative thread per QoS bucket in the normal suite and CI. `script/test.sh --self-test` verifies the strict-pool launch contract through the real wrapper and rejects worker-count overrides.
- No tags yet. The moment a network test exists, tag it (`.network` or an XCTest skip-guard keyed to an env var) and exclude it by default — never open a network connection from an untagged test.

CI also runs the public hygiene self-test and workflow checks in its existing build job. Run them locally with `./script/public-hygiene.sh --self-test` and `ruby script/workflow_self_test.rb`. The workflow checks cover secret scope, the release condition, permissions, action pins and triggers. Use `actionlint .github/workflows/ci.yml .github/workflows/release.yml` to check workflow syntax.

The path-syntax source guard runs before every suite and in lint. `PathSyntaxGuardTests` verifies that new slash or tilde checks (including split, first-index, starts-with and first/last equality or inequality in either operand order) fail with the app, daemon or CLI filename. Parenthesized and Character literals are covered. A preceding byte/scalar/helper statement does not exempt a new receiver, while continued helper and byte/scalar chains remain admitted. URL/ref/MIME exemptions identify the nominal owner and parameter signature; initializer calls and closure arrows preserve that scope, and an unrelated initializer remains guarded. `PathJoiningScalars` supplies combining-mark, ZWJ, ZWNJ, emoji-modifier, tag and Prepend-ending name cases to the filesystem owner tests.

## 5. Flaky-test policy

A flaky test is a bug. Investigate a previously passing test that fails; never skip, disable, or delete it to go green. A deliberate removal names the test in its commit and says which remaining test keeps the contract, or why the contract has been retired. Slipway's hooks hold the test floor and refuse skipped tests.

## 6. Headless / smoke

`script/build_and_run.sh --headless` **builds and links** the app for an agent/CI smoke check and prints `SMOKE OK` — build+link is the reliable unattended signal for a macOS GUI app. It does **not** assert a real headless window launch: under XCTest the main `WindowGroup` can be launch-suppressed, so window-presentation assertions may never fire (the module's hazard). The `app.launched` `os_log` signal (PLAN-01) is the in-app seam for *future* behavior tests — asserted via an injected sink in a unit test, **not** by the headless wrapper. Prefer directly-unit-testable seams over "present a window and measure."

The XCTest suite still launches Pensieve as its app host, but the split entry point in `PensieveMain` sends that process to `PensieveTestHostApp`. The test host is inert and never bootstraps `AppRuntime`, so it cannot start the scheduler, coordinator, or launch reconciliation. `script/test.sh` checks `script/check-live-defaults.py` before launching tests, and `RuntimePathGuardTests` exercises the same guard. It rejects live path defaults and real Keychain construction outside runtime path resolution. Tests supply temporary or neutral roots and in-memory credentials. These guards do not sandbox explicit I/O: a caller that deliberately names a live path can still reach it.

The test bundle's load hook sets FileService's shared folder-check deadline to 30 seconds before cases run, allowing for suite load. The app keeps its two-second deadline. Tests of that bound call `ProjectDirectoryProbeDeadline.useAppDeadline(in:)`; XCTest teardown restores the host deadline even after a failure. Cases run serially within each host, and parallel workers have separate registries. Isolated registries keep the app's two-second default.

## 7. Coverage

Use coverage to find behavior that lacks a test. A percentage alone does not show whether a check would catch a regression.

## 8. Dogfood mode — a Debug build against throwaway data

`script/dogfood.sh <Debug Pensieve.app>` runs the app against `~/PensieveSandbox/home` under two OS levers and no app code: `CFFIXED_USER_HOME` re-roots every Foundation home API (plain `$HOME` is ignored by all of them on macOS 26), and a `sandbox-exec` profile denies filesystem writes outside the fake home, kernel-enforced and inherited by git. Its tolerances: the per-user temp, cache, and `DARWIN_USER_DIR` trees and a few `/dev` nodes stay writable (Foundation needs them at launch), the launcher's own log is written by the shell outside the fence, reads are not fenced at all, and network stays open unless `--offline`. The script self-tests the fence before each launch and refuses a non-Debug bundle. It also refuses while another copy registered as the dogfood identity is installed or running outside its staged copy, read from LaunchServices and `lsappinfo`: a reopen sent to that identity would start the other copy outside the fence. Debug builds carry the bundle identifier `com.jaredatch.Pensieve.debug`, so their UserDefaults, Keychain items, and Sparkle state are separate from the released app's even without the script; the script stages a re-identified copy (`com.jaredatch.Pensieve.dogfood`) so sandbox runs do not share prefs with the live-data dev build either, and `--reset` wipes that domain; with `PENSIEVE_DOGFOOD=1` (set by the script) Sparkle is not constructed and the legacy-agent migration is not installed, the two launchd/XPC paths the fence cannot see. Before launch the script gives the fake home its own throwaway keychain (`Library/Keychains/dogfood.keychain-db`, password `dogfood`), makes it the fake home's default and whole search list, and checks that the real default and search list don't name it, so a token saved in a sandbox run never reaches the real keychain and macOS never raises its "Keychain Not Found" dialog. `--reset` wipes the fake home (that keychain with it), the dogfood prefs domain, and any dogfood Keychain items an older run left in the real keychain for a true first run; `--offline` denies network. From a Mac without the toolchain, `script/pull-dev-build.sh --host HOST --sandbox [--reset] [--offline]` does the pull and the handoff.

This is the sanctioned way to drive the GUI with cua-driver on a live machine, and the way to run the empty-store manual gates. Launch only through the script: `open`, Finder, and Xcode Run go through LaunchServices and drop the fence. The XCTest host is unaffected: it still runs against the real home (§6).
